# Database and migrations

Define schema in `apps/api/src/database/schema.ts` and relations in `apps/api/src/database/relations.ts`. Generate migrations with `pnpm --filter @kaneo/api db:generate`, inspect the resulting SQL and Drizzle metadata, and include schema and migration together. Never edit or renumber a migration already applied to an installation. Name, order and sync migrations as described in the last three sections.


Review defaults and backfill behavior against populated tables, not just an empty database. Consider indexes, foreign keys, uniqueness, deletes and nullable legacy rows. Prefer additive migrations when an older binary can still run during rollout. The `ganttpro_` prefix is used for additions in this fork's Gantt migration; a new field does not justify an unrelated rename of upstream tables.

The API migrates on startup. Use disposable PostgreSQL and the relevant `tests/api-integration/` tests to prove constraints and authorization. For schema changes, inspect the upgrade from the prior shape as well as fresh creation; the bundled image's upgrade scenario is described in `scripts/ci/README.md`. A passed unit test with a mocked database is not migration proof.

Migration `0056_ganttpro_project_members` adds project membership tables and no rows: workspace owners, administrators and roles granting `workspace:manage_settings` keep reaching every project through the full-access rule, while every other member of an existing installation loses access to all projects until they are added. `tests/api-integration/project-membership-migration.test.ts` applies migrations up to 0055, populates a database, upgrades it and checks both the empty tables and the access rule against the migrated data. If a workspace edited its `admin` role and removed `workspace:manage_settings`, those admins are no longer full-access users, so after the upgrade they lose access to existing projects until they are added (a role row that cannot be parsed falls back to the built-in role and keeps the permission).

Migration `0057_ganttpro_invitation_origin` adds `ganttpro_invitation_origin` (one row per invitation created through the project invitation routes, `source = 'project'`) and the trigger `ganttpro_invitation_project_cancel_empty`, which cancels a pending project-origin invitation when its last `ganttpro_invitation_project` row disappears, whether a route removed it, the project was deleted (cascade) or moved (`move-project.ts` deletes the rows). It backfills nothing, so every invitation that exists at upgrade time counts as a workspace invitation and is never canceled by the trigger. `tests/api-integration/project-invitation-origin-migration.test.ts` upgrades a populated 0056 database and checks the same objects on a fresh one. The trigger is hand-written SQL appended to the generated migration; keep it when regenerating.

Migration `0058_ganttpro_resource_invitation` adds the nullable `ganttpro_resource.ganttpro_invitation_id` (foreign key to `invitation.id`, ON DELETE SET NULL, indexed): the invitation sent from a person resource, cleared when the resource is linked. It backfills nothing, so every existing resource has no pending link, and an older binary ignores the column. `tests/api-integration/resource-invitation-migration.test.ts` upgrades a populated 0057 database (resources with assignments, one linked) and checks the same objects on a fresh one.

Migration `0059_ganttpro_actor_source` adds the nullable `activity.actor_via`, `activity.actor_token_hint` and `session.auth_via` (plain `text`, no default, no index). It backfills nothing: existing activity is shown as a plain user and existing sessions are not MCP sessions, and an older binary ignores the columns. `tests/api-integration/actor-source-migration.test.ts` upgrades a populated 0058 database and checks the same columns on a fresh one.

Migration `20260930053654_ganttpro_jira_integration` (the first timestamp-named fork migration; its `when` is `1790746614721`, older than `0059_ganttpro_actor_source`, and a database that applied it from the `sha-ad61d23` image recorded that value, so the runner below treats it as applied) adds five tables and backfills nothing: `ganttpro_jira_connection` (one per workspace, deleted with it), `ganttpro_jira_user_token` (deleted with its connection or user), `ganttpro_jira_mapping` (deleted with its workspace, project or user; unique with NULLS NOT DISTINCT, so PostgreSQL 15+), `ganttpro_jira_issue_link` (deleted with its task or connection; `created_by_user_id` is set null) and `ganttpro_jira_status_proposal` (deleted with its task or link; a partial unique index allows one pending row per task). Deleting a connection removes its tokens, links and proposals and keeps the mappings; an older binary ignores the tables. `tests/api-integration/jira-integration-settings.test.ts` proves the constraints and cascades on a fresh database; no populated-upgrade test exists because no row is migrated.

Migration `20261001090514_ganttpro_workspace_columns` (issued after the Jira migration) adds `ganttpro_workspace_column` (unique `(workspace_id, slug)`), `workspace.ganttpro_enforce_columns` (default false) and the nullable `column.ganttpro_workspace_column_id` (ON DELETE SET NULL). It backfills nothing, so every existing workspace has no workspace columns and enforcement off, and projects keep their columns; an older binary ignores the new objects. `tests/api-integration/workspace-columns-migration.test.ts` upgrades a populated database that is at `20260930053654_ganttpro_jira_integration` with the runner and checks the same objects on a fresh one.

Migration `20261001100317_ganttpro_adopt_upstream_assets` (issued after the workspace columns migration, so it is the newest entry; data only, created with `drizzle-kit generate --custom`, so its snapshot equals the previous one) copies data an installation created by upstream Kaneo v2.28+ left behind: project backgrounds (`project.background_object_key`, `background_mime_type`, `background_version`, upstream `0052_dear_beyonder`) into `project.ganttpro_background_*`, and `calendar_feed` rows (upstream `0053_calendar_feeds`) into `ganttpro_calendar_feed`, keeping ids and tokens so subscribed calendar URLs keep working. The column and table definitions are identical apart from the prefix, and the background object key (`workspace/<workspace>/project/<project>/backgrounds/background-<version>`, plus the configured storage key prefix) is built the same way by both builds, so the key is copied verbatim and the stored object is not moved; this assumes the upgraded installation keeps the same storage bucket and key prefix. Each copy runs only when the upstream and fork objects both exist (`information_schema` and `to_regclass` guards), fills a project only while all three fork background columns are null, and uses `ON CONFLICT DO NOTHING` for feeds, so it is idempotent and never overwrites fork data. The upstream columns and table are not dropped, so an upstream image can still run against the database; a background replaced or deleted through this fork deletes the object, which the untouched upstream column then still references. The runner applies every entry after `0050_resumable_github_import` whose `when` is not recorded, so a database written by an upstream release that recorded a newer `created_at` still gets this migration (Drizzle's own migrator would skip it). `tests/api-integration/upstream-assets-migration.test.ts` upgrades a populated database that is at `20261001090514_ganttpro_workspace_columns` with the runner, with and without the upstream objects and with a newer recorded migration, and `scripts/ci/upgrade.mjs` seeds and verifies a background and a calendar feed when the source release has them.

Migration `20261005125019_ganttpro_task_estimate` (the newest entry after `20261001100317_ganttpro_adopt_upstream_assets`) adds `task.ganttpro_estimate_minutes` (nullable integer, check `>= 0` when set) and `task.ganttpro_estimate_unit` (`text NOT NULL DEFAULT 'hours'`). It is additive and backfills nothing: every existing task has no estimate and the default unit, and an older binary ignores both columns. `tests/api-integration/task-estimate.test.ts` covers persisting, clearing and rejecting an estimate on a fresh (migrated) database; no populated-upgrade test exists because no row is migrated.

## Migration names

`apps/api/drizzle.config.ts` sets `migrations.prefix` to `timestamp`. `db:generate` names a new migration `YYYYMMDDHHMMSS_<name>.sql`, where the prefix is the UTC second of authoring (`date -u +%Y%m%d%H%M%S`), and its snapshot `meta/YYYYMMDDHHMMSS_snapshot.json`. Always pass `--name ganttpro_<description>`: `apps/api/src/utils/adopt-existing-database.ts` identifies this fork's migrations by `ganttpro` in the tag. The four-digit files `0000` to `0059` are frozen. Synced upstream migrations keep their upstream four-digit names. A timestamp prevents file-name collisions between branches and with upstream, and `0059_snapshot.json` sorts before every timestamp snapshot, so drizzle-kit keeps the correct parent. A timestamp does not prevent a conflict in `meta/_journal.json` or two snapshots with one `prevId` when two lineages each add a migration.

## How migrations apply

`apps/api/src/database/run-migrations.ts` applies the folder at startup (`apps/api/src/index.ts`) and in `pnpm --filter @kaneo/api db:migrate` (`apps/api/scripts/migrate.ts`). Do not use `drizzle-kit migrate`: it skips a migration merged late. The runner keeps Drizzle's table `drizzle.__drizzle_migrations` and its rows (`hash`, `created_at` = the entry's `when`). It runs in one transaction behind a PostgreSQL advisory lock, so API instances that start together apply each migration once, and a failure rolls back the whole run.

- Entries up to `LEGACY_WATERMARK_LAST_TAG` (`0050_resumable_github_import`) keep Drizzle's rule: an entry runs only if its `when` is greater than the newest recorded `created_at`. Older installations applied this upstream history with that rule and skipped three entries whose `when` is out of order (`0006`, `0025` and `0026`). `0025_early_owl` is a plain `CREATE TABLE`, so to run it again would stop the start.
- Every later entry runs when its `when` is not recorded, as monize runs every file that it has not recorded. A migration merged late with an older `when` still runs on an upgraded database, after the newer migrations. The apply order is journal order on a fresh database and merge order on an upgraded one, so a migration must not depend on the order of a migration that is not merged yet.
- The runner identifies an entry by its `when`, not by its file name. A renamed file does not run again. Do not rename a migration all the same: tests, documents and the upstream sync refer to tags.

`reconcileMigrationJournal` (`apps/api/src/utils/adopt-existing-database.ts`) runs before the runner. It rewrites the baseline rows only when `public.account` exists and no recorded `created_at` equals the `when` of a baseline entry: an old fork installation built from a regenerated baseline. A database created by upstream recorded the same `when` values as this journal, so the function leaves it as it is and the runner applies what the database does not have. `tests/api-integration/migration-runner.test.ts` (CI job `integration`) covers a fresh database, a late merge, databases created by upstream at its `0055` and at `0045`, a rollback and two concurrent runs.

`tests/api/database/migration-journal.test.ts` (CI job `unit`) fails when an entry up to the cutoff is out of order (the three historical entries are grandfathered), when a later entry is not newer than the cutoff, when SQL files and journal entries do not match, when two snapshots share a `prevId`, or when a new fork migration does not use the `<timestamp>_ganttpro_` form.

## Upstream sync

`.github/workflows/upstream-sync.yml` opens the sync pull request. Its report lists legacy number clashes and upstream migrations that are older than this fork's newest migration; on upgraded fork databases those run after this fork's newer migrations. To resolve the merge:

1. Keep every fork entry in `meta/_journal.json` with its position and `when`. Never regenerate or renumber a fork migration: each installation that applied it recorded its `when`.
2. For each new upstream migration, first check whether a fork migration already contains the change (the changes of upstream `0051` to `0053` are part of `0051_ganttpro_additions`, with `ganttpro_` object names). If it does, remove the upstream SQL and snapshot files. If it does not, append the entry after the last one and keep upstream's file name and `when`, so that a database created by upstream finds it recorded. Make sure that it does not depend on the order, for example on a table or column that a newer fork migration changed.
3. Link the snapshot chain again, so that no two snapshots share a `prevId`. The lexicographically last snapshot must describe the merged `schema.ts`; otherwise the next `db:generate` repeats upstream DDL.
4. Run the journal test, `tests/api-integration/migration-runner.test.ts` and the relevant migration integration tests.

Known gaps: `reconcileMigrationJournal` creates the journal table outside the advisory lock, so two instances that start together on a fresh database can fail on the first start (not tested). Only review checks that an upstream migration works in an order that upstream did not test. An entry after the cutoff with a `when` that is not newer than the cutoff would follow the watermark rule; the journal test rejects it.
