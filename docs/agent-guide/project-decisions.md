# Accepted project decisions

These decisions were accepted for this Kaneo fork. **Accepted is not implemented.** The [invariant index](invariants.md) tracks what the code and tests enforce today; the [scheduling contract](scheduling.md) and [deployment contract](deployment.md) describe the current paths. Implement the changes in focused PRs, preserve existing installation data, and update invariant statuses only when the required proof exists.

| ID | Accepted decision | Implementation state and proof needed |
| --- | --- | --- |
| DEC-SCHED-01 | The API is the authority for dependency-aware schedule changes. All clients must use an operation that calculates or validates the dependency graph. Other date-writing routes must not silently persist a conflicting schedule. | Pending. The browser currently computes the cascade and the API validates dates, not dependency consistency. Specify the API contract, permission boundaries and treatment of existing schedules; test writes from UI and other API clients. See KAN-SCHED-005. |
| DEC-SCHED-02 | Moving or resizing a task and shifting its affected dependents is one API operation and one database transaction. A failure must not leave a partially moved schedule. | Pending. The dragged task and dependents currently use separate requests. Test rollback after a failure, persisted dates, reload, and event delivery semantics without claiming that database commit alone guarantees event delivery. See KAN-SCHED-006. |
| DEC-SCHED-03 | A `blocks` relation between projects in the same workspace participates in the workspace-wide cascade. Until implemented, make clear in the UI and API documentation that a cross-project link does not automatically move its target. | Pending. The current cascade sees only tasks loaded for the active project. Test scope and permissions across projects, a cross-project chain, conflicting constraints and realtime refresh on both sides. Never cross workspace boundaries. See KAN-SCHED-007 and KAN-AUTH-001. |
| DEC-SCHED-04 | A calendar must contain at least one working weekday: reject working-days mask `0` on new settings writes and give existing workspaces with `0` an explicit correction path. Do not silently rewrite an existing calendar to Monday-Friday. | Pending. Test the API rejection and the existing-data path, then the next-working-day cascade. See KAN-SCHED-004. |
| DEC-SCHED-05 | Concurrent creation of `blocks` and `subtask` edges cannot introduce a cycle. Serialize the graph check and write for the relevant workspace. | Pending. Sequential cycle tests exist; add a PostgreSQL concurrency test with two competing edges. See KAN-SCHED-001. |
| DEC-RELEASE-01 | Current branch images are preview artifacts only. Before a branch image can be treated as deployable, publishing must require successful CI for the exact source SHA. | Preview-only rule applies now; the publication gate is pending. Verify the CI-to-build SHA binding and workflow behavior, including reruns. See KAN-RELEASE-001. |
| DEC-AGENT-01 | Keep one concise root `AGENTS.md`, scoped contracts and an invariant index with stable IDs. Split the invariant index into topical files only if it becomes hard to navigate; keep a single index, unique IDs and automated link/path checks. | The guide and checks are included in this documentation change; verify they are merged into a target branch before claiming they apply there. |
| DEC-CONTRIB-01 | Deliver agent-guide and guard changes separately from Gantt behavior changes. A functional PR names affected invariant IDs and their actual statuses; documentation alone does not change a status to enforced. | The PR template and guide include this convention. It does not require one PR per invariant. |

Implement the scheduling decisions in this order: API authority and atomic operation together, workspace-wide cross-project behavior, calendar validation, then concurrent cycle protection. A calendar or cycle fix may be delivered earlier as an independent focused change. Keep preview-image gating and agent-guide delivery as separate workstreams. Revisit this document when a deliberate product decision changes; do not change it merely to make existing code appear compliant.
