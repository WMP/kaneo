# API and workspace boundaries

The API owns authorization. Use `@kaneo/permissions` and the route's `requireWorkspacePermission` middleware; verify both the caller's action permission and the workspace membership of every referenced resource. Hiding a button is only a UI affordance. Cross-project relations may join projects inside one workspace, but must never link foreign-workspace tasks. See `apps/api/src/task-relation/controllers/create-task-relation.ts` and `tests/api-integration/task-relation-boundaries.test.ts`.

Define public routes with `createRoute` and mount them through `apiRouter()` in `apps/api/src/openapi.ts`; keep Zod request schemas in a feature's `schema.ts` and named `.openapi(...)` response schemas in `response.ts`. Route middleware declared in `createRoute({ middleware })` runs **before** request validators, so it cannot rely on `c.req.valid()`. Use `HTTPException` for expected failures. Valibot in `apps/api/src/plugins/` and `apps/api/src/ws/` is internal configuration validation, not the public API pattern.

Keep handlers thin, behavior in controllers/focused utilities, and changes to `apps/docs/openapi.json` in step with public contract changes (`pnpm openapi:check:fix`, then `pnpm openapi:check`). Follow authorization and response changes into the typed `@kaneo/libs` client, web fetchers, hooks, published stdio MCP package, API's MCP HTTP routes, API keys and webhooks where they consume the same behavior. A new endpoint does not automatically need a new MCP tool; decide and record the reason.

Role delegation: a non-owner may only invite, re-send an invitation for, or assign a role whose permissions are a subset of their own, and may not change their own role. Better Auth checks `invitation:create` and `member:update` but not the contents of the role being granted, so `apps/api/src/utils/role-delegation.ts` (`assertCanAssignRole`) closes that gap: `beforeCreateInvitation` covers new invitations, and `beforeUpdateMemberRole` covers role changes after Better Auth's own role validation and `member:update` check. That hook is not told who is acting, so it reads the actor from `getCurrentAuthContext()` (`@better-auth/core/context`): the endpoint context holds the session Better Auth's own session middleware resolved after the bearer and API-key plugins ran. The global `hooks.before` cannot do this, because Better Auth runs it before plugin hooks with the original request context, where `getSessionFromCtx` returns no session for `Authorization: Bearer` or `x-api-key` requests. `invite-member` with `resend: true` skips every organization hook, so it stays in `hooks.before`, which resolves the session through `auth.api.getSession` (dispatching through all plugins; a failing lookup rejects the request, only a lookup without a session defers to Better Auth's 401). That lookup re-runs the api-key plugin's usage claim, so a re-send authenticated with `x-api-key` counts twice against the key's rate limit and `remaining`; this is a known limitation and no custom key resolver is used. The hook uses `body.organizationId || activeOrganizationId` like Better Auth, and checks the role of every live (pending, unexpired) invitation for that email; expired rows are ignored as Better Auth ignores them, and with none Better Auth creates a new invitation that `beforeCreateInvitation` checks. Owners and instance administrators bypass the subset rule; `owner` is never assignable by anyone else. `GET /api/workspace/{id}/assignable-roles` lists what the caller may assign, for the UI.

Project membership: access to a project's data comes from a `ganttpro_project_member` row, except for full-access users (instance administrator, workspace `owner`, or a workspace role granting `workspace: ["manage_settings"]`). `resolveProjectAccess(userId, projectId)` in `apps/api/src/utils/project-access.ts` is the single decision: workspace membership first (a stale project row grants nothing), then full access, then the project row, whose role must resolve in the workspace catalog and is never `owner`. `workspaceAccess` (`apps/api/src/utils/workspace-access-middleware.ts`) resolves the project of every project-scoped resource, answers 403 `You don't have access to this project`, and sets `projectAccess`, so `hasWorkspacePermission` checks the statements of the caller's role IN that project (every project for a bulk request), while workspace-scoped routes and `workspaceIdOverride` keep using the workspace role. A resolver that does not go through `workspaceAccess` must call `assertProjectAccess` or `resolveProjectAccess` itself; `accessibleProjectIds` is the filter for list endpoints. Project members are managed through `apps/api/src/project-member/` with the same delegation rule as workspace roles (`rolesWithin`), and a workspace role that a project membership still names cannot be deleted or renamed (`hooks.before` in `apps/api/src/auth.ts`). See [the plan](../plans/project-membership.md).

Never send secrets or private workspace fields to other tenants through API responses, activity, events, WebSockets, MCP, logs or exports. Test both an allowed user and a user from another workspace through the real API or database-backed integration path, not only a mocked permission helper.
