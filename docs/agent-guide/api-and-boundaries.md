# API and workspace boundaries

The API owns authorization. Use `@kaneo/permissions` and the route's `requireWorkspacePermission` middleware; verify both the caller's action permission and the workspace membership of every referenced resource. Hiding a button is only a UI affordance. Cross-project relations may join projects inside one workspace, but must never link foreign-workspace tasks. See `apps/api/src/task-relation/controllers/create-task-relation.ts` and `tests/api-integration/task-relation-boundaries.test.ts`.

Define public routes with `createRoute` and mount them through `apiRouter()` in `apps/api/src/openapi.ts`; keep Zod request schemas in a feature's `schema.ts` and named `.openapi(...)` response schemas in `response.ts`. Route middleware declared in `createRoute({ middleware })` runs **before** request validators, so it cannot rely on `c.req.valid()`. Use `HTTPException` for expected failures. Valibot in `apps/api/src/plugins/` and `apps/api/src/ws/` is internal configuration validation, not the public API pattern.

Keep handlers thin, behavior in controllers/focused utilities, and changes to `apps/docs/openapi.json` in step with public contract changes (`pnpm openapi:check:fix`, then `pnpm openapi:check`). Follow authorization and response changes into the typed `@kaneo/libs` client, web fetchers, hooks, published stdio MCP package, API's MCP HTTP routes, API keys and webhooks where they consume the same behavior. A new endpoint does not automatically need a new MCP tool; decide and record the reason.

Role delegation: a non-owner may only invite, re-send an invitation for, or assign a role whose permissions are a subset of their own, and may not change their own role. Better Auth checks `invitation:create` and `member:update` but not the contents of the role being granted, so `apps/api/src/utils/role-delegation.ts` (`assertCanAssignRole`) closes that gap: `beforeCreateInvitation` covers new invitations, and `beforeUpdateMemberRole` covers role changes after Better Auth's own role validation and `member:update` check. That hook is not told who is acting, so it reads the actor from `getCurrentAuthContext()` (`@better-auth/core/context`): the endpoint context holds the session Better Auth's own session middleware resolved after the bearer and API-key plugins ran. The global `hooks.before` cannot do this, because Better Auth runs it before plugin hooks with the original request context, where `getSessionFromCtx` returns no session for `Authorization: Bearer` or `x-api-key` requests. `invite-member` with `resend: true` skips every organization hook, so it stays in `hooks.before`, which resolves the session through `auth.api.getSession` (dispatching through all plugins; a failing lookup rejects the request, only a lookup without a session defers to Better Auth's 401). That lookup re-runs the api-key plugin's usage claim, so a re-send authenticated with `x-api-key` counts twice against the key's rate limit and `remaining`; this is a known limitation and no custom key resolver is used. The hook uses `body.organizationId || activeOrganizationId` like Better Auth, and checks the role of every live (pending, unexpired) invitation for that email; expired rows are ignored as Better Auth ignores them, and with none Better Auth creates a new invitation that `beforeCreateInvitation` checks. Owners and instance administrators bypass the subset rule; `owner` is never assignable by anyone else. `GET /api/workspace/{id}/assignable-roles` lists what the caller may assign, for the UI.

Project membership: access to a project's data comes from a `ganttpro_project_member` row, except for full-access users (instance administrator, workspace `owner`, or a workspace role granting `workspace: ["manage_settings"]`). `resolveProjectAccess(userId, projectId)` in `apps/api/src/utils/project-access.ts` is the single decision: workspace membership first (a stale project row grants nothing), then full access, then the project row, whose role must resolve in the workspace catalog and is never `owner`. `workspaceAccess` (`apps/api/src/utils/workspace-access-middleware.ts`) resolves the project of every project-scoped resource, answers 403 `You don't have access to this project`, and sets `projectAccess`, so `hasWorkspacePermission` checks the statements of the caller's role IN that project (every project for a bulk request) for `project`, `task`, `label` and the like, while the workspace-level resources `workspace`, `member`, `invitation`, `organization`, `ac` and `team` are always evaluated against the WORKSPACE role (a project `admin` with the workspace role `viewer` cannot read integration secrets or set external comment authors), as are workspace-scoped routes and `workspaceIdOverride`. Explicit exception: the project invitation routes and the project member routes decide `invitation:create`, `invitation:cancel` and `member:*` by the caller's effective PROJECT statements (a person invites within their own scope), not by the workspace role; the workspace role a project invitation grants is still capped by the inviter's own workspace role. A resolver that does not go through `workspaceAccess` must call `assertProjectAccess` or `resolveProjectAccess` itself; `accessibleProjectIds` is the filter for list endpoints. Project members are managed through `apps/api/src/project-member/`, which checks `member:*` against the effective PROJECT statements itself and applies the same delegation rule as workspace roles (`rolesWithin`). A workspace role that a project membership or pending project invitation still names cannot be deleted or renamed: `guardRoleChange` in `apps/api/src/utils/project-role-guard.ts` runs in `hooks.before` of `apps/api/src/auth.ts`, but only answers a caller Better Auth would allow (a member of that workspace holding `ac:delete` or `ac:update`, owners included, instance administrators get no special treatment) and never for `owner`, so it never leaks before authorization; it re-runs the API-key usage claim through `auth.api.getSession`, a known limitation. The upgrade drops nothing for full-access users, but a workspace that removed `workspace:manage_settings` from its `admin` role leaves those admins without access to existing projects until they are added. See [the plan](../plans/project-membership.md).

A list, search, count, export, activity feed or notification that spans projects filters by the caller's project scope: resolve `accessibleProjectIds` once (a route that already resolved access to one project reuses it through `visibleProjectIdsFor`), then apply `projectScopeCondition` from `apps/api/src/utils/project-scope-filters.ts` in SQL (`null` is every project, an empty list matches nothing), so rows, counts, names and the task on the far side of a relation stay hidden. Predicates across workspaces (search, notifications) use `resolveUserProjectScope` with `userProjectScopeSql`. A relation with a hidden end is dropped, its activity too, and a write on it answers 404. Notifications about a task need project access to be listed, created and delivered (`notificationResourceAccess`, `canReceiveResourceNotification`), an assignee must be able to open the task's project (`assertProjectAssignableUser`), and `getWorkspaceMembers` limits a restricted caller to people who share a project unless their workspace role manages members.

Project invitations: `apps/api/src/project-invitation/` (`POST` and `GET /api/project/{id}/invitations`, `DELETE .../{invitationId}`, `POST .../{invitationId}/resend`, `GET /api/project/{id}/member-candidates`) invite somebody who is not in the workspace yet to one project with a chosen workspace role and project role. `invitation` is a workspace-level resource, but these routes are the explicit exception described above: each checks `invitation:create` or `invitation:cancel` (candidates: `member:create`) against the caller's effective PROJECT statements and the API key scope itself (`delegation.ts`), while the workspace role being granted is capped by the inviter's workspace role. The workspace role goes through `assertCanAssignRole` and the project role through `assertAssignableProjectRole` (`owner` is never granted, for either); cancel and resend need both roles of the existing invitation within the caller's. Errors are JSON with a `code` (`ROLE_EXCEEDS_YOUR_PERMISSIONS`, `ALREADY_WORKSPACE_MEMBER`, `INVITATION_ROLE_CONFLICT`, ...). The route writes Better Auth's `invitation` row itself, so it repeats what `invite-member` enforces: the 48 hour expiry and the limit of 100 pending invitations (`constants.ts`, also handed to Better Auth in `auth.ts`), the cloud guest and disposable-address gates (creating and re-sending), the cloud rate limit of 5 per minute per user shared by creating and re-sending (`rate-limit.ts`, in-process counters), and the shared email sender `apps/api/src/invitation/send-invitation-email.ts`. A `ganttpro_invitation_project` row may only name a project of the invitation's workspace (`upsertInvitationProject`). Acceptance stays Better Auth's `/organization/accept-invitation` (email match by Better Auth): `beforeAcceptInvitation` refuses somebody who already is a workspace member (`ALREADY_WORKSPACE_MEMBER`, for plain workspace invitations too, since Better Auth would add a duplicate member row), drops leftover project memberships of a person who is not a member yet, and `afterAcceptInvitation` (`apps/api/src/project-invitation/accept.ts`) creates the memberships in one transaction from the projects that still belong to the workspace (skipping full-access people and roles that no longer resolve) and deletes the invitation's rows. Memberships are inserted with `ON CONFLICT DO NOTHING`, never overwriting a row. If that fails, the acceptance is reverted (member row deleted and the person's project sockets closed like after a member removal, invitation pending again, the session's active workspace cleared) so no silent half state remains; only when the revert fails too is the person left in the workspace without the projects. Attaching a project, cancelling and re-sending take a per-email advisory lock and then lock the invitation row `FOR UPDATE` (so the origin trigger's cancel from a project move or delete cannot interleave), re-read the invitation there and judge the roles on that row, with the role lookups on the same transaction; cancelling accepts a role that no longer resolves (inert), like the member API. `ganttpro_invitation_origin` (migration 0057) marks invitations made through these routes: only such an invitation is canceled when its last project goes away (a trigger covers removal, deletion and move of the project), and a project may be attached to, and a re-send done for, a workspace invitation only by somebody holding `invitation:create` in their workspace role (the canonical `hasWorkspacePermission` decision; `WORKSPACE_INVITATION_EXISTS`). Kaneo's invitation read routes add `projects: { id, name, role }[]`, on the public one only for an invitation that can still be accepted.

Resources and invitations (stage 3): a person resource (`ganttpro_resource`, `apps/api/src/resource/`) can be invited (`POST /api/resource/{id}/invite`), linked to an existing member (`POST .../link`, `.../unlink`) and lists its projects to pre-select (`GET .../invite-defaults`). Inviting reuses `createInvitationForProjects` (`project-invitation/controllers/create-project-invitation.ts`), the core of the project invitation route: cloud gates, `assertInvitableWorkspaceRole`, `assertInvitableProjectRole` against the caller's access to EACH project, `invitation:create` in EACH project (`assertInvitationPermission`, evaluated on the effective project statements and the API key scope), the per-email lock, the origin row and the email (access to the projects is resolved in one query, `resolveProjectAccesses`); one invitation with several project rows, all or nothing. The route also needs `project:update` in the workspace role (resource management); linking needs it and `member:update` (workspace role), since it decides which account holds the assignments. The resource remembers the invitation (`ganttpro_invitation_id`, written in the invitation's transaction). Acceptance (`afterAcceptProjectInvitation`) links the resources in the SAME transaction as the project memberships (`linkInvitedResources`), so a failure takes the revert path above: `moveResourceAssignmentsToUser` (`resource/transfer-assignments.ts`) converts the resource's assignments on tasks of projects the account can open (its new memberships, or every project for full access) into user assignments and merges an assignment the account already had on the task (the higher `units`, never the sum; `work` kept from either side), leaves the others on the resource and recomputes `task.userId`. The `task.assignee_changed` events are published after the commit with `source: "resource_link"` (activity, WebSocket and integrations; no notification) and a failing publish is logged, never undone. The workload has one row for the account for a caller who may see that account (`foldTargetId`, the members-list rule; anybody else keeps the resource's own row): a linked resource has none then, its remaining assignments count in the account's row (merged per task). The resource responses carry `linked` (for everyone), `userId` and `user` (only when the caller may see that member, the members list rule, else null) and `invitation` (`pending` or `expired`, only for a caller who may invite in the workspace role or in a project; never the invitation id). The link and the acceptance transactions run in `retryTransaction` (3 attempts on a deadlock or serialization failure) and lock the task rows before the assignment rows. Leaving runs its cleanup steps (memberships, unlink, sockets) independently (`runIndependently`): each runs, each failure is logged, the first is thrown. "May the caller invite in a project" is one function, `projectsCallerMayInviteTo`, for the invite dialog's list and for the invitation-state visibility. Unlinking does not move assignments back; removing a member, leaving and joining afresh unlink the account's resources (`unlinkUserResources`), account deletion does it by ON DELETE SET NULL.

Never send secrets or private workspace fields to other tenants through API responses, activity, events, WebSockets, MCP, logs or exports. Test both an allowed user and a user from another workspace through the real API or database-backed integration path, not only a mocked permission helper.
