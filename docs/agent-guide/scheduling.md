# Gantt scheduling contract

Read the implementation and its tests before changing these behaviors. The UI calculates a cascade and submits dates through the API; the API persists and validates dates, but it does not independently recompute the dependency schedule. The accepted future behavior is in [project decisions](project-decisions.md); do not confuse that target with the current implementation.

## Dates and calendar

Tasks have optional `startDate` and `dueDate`; API date parsing and `validateDateRange` live in `apps/api/src/utils/validate-dates.ts`. The Gantt's timeline and drag math use local calendar days (`apps/web/src/components/gantt/timeline.ts` and `apps/web/src/components/gantt/gantt-task-bar.tsx`); do not replace calendar-day arithmetic with milliseconds divided by 86,400,000 across DST boundaries. Holidays are date-only values stored at UTC midnight: `apps/web/src/components/gantt/gantt-working-calendar.ts` extracts the ISO date portion for holidays, while `toDateKey` uses a local day for displayed tasks. Test a non-UTC browser time zone when changing this boundary.

`workspace.workingDays` is a seven-bit mask in JavaScript `Date#getDay()` order (Sunday bit 0); default 62 enables Monday-Friday. Holidays override a working weekday. `apps/web/src/components/gantt/gantt-working-calendar.ts` provides the common predicate; `tests/api-integration/calendar.test.ts` covers the API settings. A shifted dependent's start may be nudged forward to the next working day, preserving its span. The directly moved task is not nudged by the cascade. **Known gap:** the API accepts mask `0` (no working weekdays), but the cascade's forward search stops after 366 days and can then place a dependent on a non-working day. Do not promise a valid next working day for every accepted calendar.

## Relations and movement

For `blocks`, `sourceTaskId` blocks `targetTaskId`. `dependencyType` is `fs`, `ss`, `ff` or `sf`; positive `lagDays` is lag and negative is lead. **Finish-to-start (`fs`) means the successor starts on the next day after the predecessor's end day, plus the lag** (`end + 1 + lag`, then nudged to the next working day when a calendar is available); task dates are whole days and a task occupies its end day, so a same-day start would overlap. `ss`, `ff` and `sf` tie two points of the same kind and stay same-day (`start + lag` / `end + lag`). The single offset lives in `apps/web/src/components/gantt/gantt-dependency-rules.ts` (`FS_HANDOFF_DAYS`) and is used by the cascade, the derived schedule and the critical path so they cannot drift. This changed the earlier same-day cascade (KAN-SCHED-002 domain, status unchanged): a dated successor whose start equals its `fs` predecessor's end is now pushed forward by one day. Non-`blocks` relations retain `fs`/`0` storage defaults and do not schedule. Cross-project links within one workspace are supported; foreign-workspace endpoints are refused. The API rejects directional cycles for `blocks` and `subtask` on creation; `related` has no directional cycle. See `apps/api/src/task-relation/controllers/` and `tests/api-integration/task-relation-*.test.ts`.

`computeDependencyCascade` in `apps/web/src/components/gantt/gantt-dependency-cascade.ts` only shifts **forward** and preserves the start-to-due span. The moved task is fixed at its new dates. Only scheduled tasks in the current project's `tasksById` participate; an absent or cross-project target is not shifted. A `must_start_on` task is pinned, and a shift that would have reached it does not propagate through it. `start_no_earlier_than` and `finish_no_later_than` are not pinning: deadline violations are reported separately by `apps/web/src/components/gantt/gantt-constraint-violations.ts`. Tests live in `apps/web/src/components/gantt/gantt-dependency-cascade.test.ts`.

A `blocks` successor that has no dates of its own is given a **display-only** position on the Gantt, derived from its placed predecessor(s) per dependency type and lag by `deriveUndatedSuccessorSchedules` in `apps/web/src/components/gantt/gantt-derived-schedule.ts` (pure; `gantt-derived-schedule.test.ts`), so its dependency line has a read-only bar to land on instead of vanishing. It applies to an undated task of another project in the same workspace and to an undated task of the project on screen (a task that already has a row, including a summary parent's rolled-up span, is never a candidate). It is drawn as a distinct (dotted, dimmer) row with its own tooltip (`apps/web/src/components/gantt/gantt-external-task-bar.tsx`, `gantt-external-rail-entry.tsx`); the bar and the rail entry open the task (an own-project row in this page's task sheet, a cross-project row on its own project's task route, as the relations panel does); the bar stays read-only (no drag, resize or link handle). The rail shows the task's status pill like an own row; for a cross-project row it is the status slug from the relation summary (the other project's board is not loaded, so no column name). **Nothing is persisted** — this is presentation only and does not shift the target, join it to the cascade, or otherwise change KAN-SCHED-007 / DEC-SCHED-03, which remain the accepted, still-unenforced target for server-side cross-project scheduling.

- Without an effort estimate the derived row is a single-day marker (`start === end`).
- With an estimate (`task.estimateMinutes`, see below) the bar spans `max(1, ceil(estimateMinutes / 480))` days, counted over working days only when the workspace calendar is available (non-working days are skipped when extending the end) and over calendar days otherwise. The estimate never changes a task that has dates of its own.
- Anchors use the cascade's arithmetic (`edgeForcedDeltaDays`), so finish-to-start places the successor's start on the **day after** the predecessor's end day plus lag (`end + 1 + lag`, then nudged to the next working day, so the bars never overlap): `fs` start = predecessor end + 1 + lag, `ss` start = predecessor start + lag, `ff` end = predecessor end + lag, `sf` end = predecessor start + lag; for `ff`/`sf` the start is counted backwards over the duration. An anchor on a non-working day is nudged forward. With several predecessors every edge becomes the earliest start it allows and the latest wins.
- Chaining: a derived task that has an estimate can anchor its own successors (A dated, B undated with an estimate, C undated), processed in dependency order. A derived marker without an estimate does not anchor further tasks. A task on a cycle, or downstream of one, stays unplaced.
- A task that has an estimate and **exactly one** own date is not a derived row: it keeps its real bar (see "Estimate and date range" below), and it can anchor derived successors like any dated task, using its computed span.
- **Portfolio.** The workspace portfolio (`apps/web/src/routes/_layout/_authenticated/dashboard/workspace/$workspaceId/portfolio.tsx`, `apps/web/src/components/gantt/gantt-portfolio.ts`) uses the same pure functions (`deriveTaskScheduleWithEstimate`, `deriveUndatedSuccessorSchedules`) with the same workspace calendar predicate, in one memoized pass over the payload, so a task sits on the same days as on its project Gantt. `GET /api/project/portfolio` returns `estimateMinutes`/`estimateUnit` per task and `undatedSuccessorDependencies`: `blocks` edges, same- or cross-project, whose **target** has neither date, between tasks of the projects the caller may see and neither archived (`apps/api/src/project/controllers/get-portfolio.ts`; the existing `dependencies` list, the cross-project edges drawn as lines, is unchanged). There is no new cap: undated tasks were already returned (last in each project), and the edge list is bounded by the blocks edges into undated visible tasks. Derived rows are read-only (the portfolio has no drag), drawn dotted and dimmer with the derived tooltip (`gantt-portfolio-task-bar.tsx`), and, unlike on the project Gantt, **do** roll up into the project summary bar (span and progress), so a project with only estimated, dependency-placed tasks still shows its span. Differences from the project Gantt: the portfolio does not load subtask relations, so an undated summary parent that has an estimate and a predecessor is drawn as a derived row instead of its rolled-up span, and an archived dated predecessor does not anchor a derivation.
- **Known gap:** the derived rows are covered by pure tests and a jsdom render test (`gantt-derived-own-task.test.tsx`, `gantt-derived-cross-project-successor.test.tsx`); no browser scenario checks the dependency line or the interaction.

The UI sends a cascade as `updateSchedule` in one bulk API call. `apps/api/src/task/controllers/bulk-update-tasks.ts` validates each selected date range, updates the scheduled tasks in a transaction and emits `task.updated` per task. When changing this path, test what the UI sent, what PostgreSQL stored, activity/realtime changes and behavior after reload; `tests/api-integration/bulk-task-schedule.test.ts` covers part of that path.

## Estimate and date range

**Rule:** a task with an effort estimate must not have a complete date range: `estimateMinutes IS NULL OR startDate IS NULL OR dueDate IS NULL`. Estimate plus a start only, plus a due only, or plus no dates is allowed; an estimate of `0` is still an estimate. The statement (`assertEstimateExcludesDateRange`, `apps/api/src/task/estimate.ts`) is evaluated against the **merged** state, the row as it will be after the write:

- create (`POST /api/task/{projectId}`): the incoming estimate and dates; `PUT /api/task/{id}`: the incoming dates (the full update replaces both, an omitted date is cleared) with the incoming estimate, or the stored one when the estimate is omitted (so `estimateMinutes: null` together with two dates is fine); `PUT /api/task/due-date/{id}`: the stored estimate and start date with the new due date; bulk `updateDueDate`: each task's stored estimate and start date; bulk `updateSchedule`: each entry's dates (an entry replaces both dates of the task, an omitted or null one is cleared) with the stored estimate. A violation is a **400** with the stable message `A task with an effort estimate cannot have both a start date and a due date. Remove the estimate or clear one of the dates.`, before anything is written (the bulk operations validate every task first).
- The check constraint `ganttpro_task_estimate_no_full_date_range` ([database](database.md)) enforces the same statement for paths that skip the API; the app error handler turns that violation into the same 400 instead of a 500.
- Paths that cannot produce the state: task import only inserts new tasks and accepts no estimate; duplicate does not copy the estimate; the GitHub, Gitea, GitLab and Jira integrations never write `startDate`/`dueDate` or the estimate (Jira reads dates for outbound drafts and writes only status), so no integration sync can hit the rule and none needed a skip-or-clear policy. A **future** sync that writes dates must either send the merged state through `assertEstimateExcludesDateRange` or skip the write and log it; failing a whole sync on the constraint is the one thing to avoid. MCP tools call the REST routes, so `update_task`, `update_task_due_date` and `create_task` return the 400 message as a tool error (`isError`), and the tool descriptions state the rule.
- Web: in the create-task form and the task details the other date picker is disabled with a hint while an estimate and one date are set (`isDateBlockedByEstimate`), the estimate field is disabled with a hint while both dates are set (`hasFullDateRange`), and a refusal that still reaches the API is shown through the existing error toast (`apps/web/src/lib/estimate.ts`, `components/task/estimate-editor.tsx`, `task-estimate-popover.tsx`, `task-start-date-popover.tsx`, `task-due-date-popover.tsx`, `components/shared/modals/create-task-modal.tsx`).

**Gantt consequence.** Such a task is a dated task with a real bar row, but one date has no length, so the span is derived from the estimate (`apps/web/src/components/gantt/gantt-estimated-span.ts`, pure, `gantt-estimated-span.test.ts`): start only: `end = start + (durationDays - 1)` working days; due only: `start` counted backwards from the due date; `durationDays = max(1, ceil(estimateMinutes / 480))`, working days from the workspace predicate (calendar days without one). The task's own date is not nudged, a milestone is not sized, and a task with both dates (never stored with an estimate) keeps its range. **The derived end/start is display-only and is never persisted as the missing date.**

- The route builds `ownScheduleByTaskId` from these spans, so the bar, summary rollups, the critical path, the dependency cascade and derived successors (which anchor on the span like on any dated task) all see them. Cross-project relation endpoints use the same derivation.
- Drag: `GanttTaskBar` moves the span and persists only the date the task has (`ownDatePayload`: start-only shifts the start, due-only shifts the due date; the other date is sent as `null`). **Resize is disabled** for such bars (both handles are not rendered), because resizing would create the missing date; changing the length means changing the estimate in the task details. Converting a resize into an estimate edit was not done.
- Cascade: `computeDependencyCascade` takes `estimatedTasks`; a shifted estimated task is re-derived from its shifted own date (start-only: the end is counted forward over working days; due-only: the due date moves later until the re-derived start is not earlier than the constraint allows) instead of preserving the calendar span. `handleTaskDatesCommitted` in the Gantt route then sends only the own date of such a task in the bulk `updateSchedule` payload, so the API never receives a full range for an estimated task (`bulk-update-tasks.ts` accepts a start-only or due-only entry; an entry always replaces both dates).
- **Known gaps:** a stale client that still thinks the task has no estimate gets the 400 on a drag; no browser scenario covers the drag, the cascade payload or the disabled pickers (jsdom component tests and pure tests only).

## Other schedule fields and gaps

`isMilestone` is a Gantt marker; `progress` is a bounded percentage. `estimateMinutes` (nullable integer, `0..1,000,000`, database check `ganttpro_task_estimate_minutes_range`) is an effort estimate and `estimateUnit` (`hours` or `days`, default `hours`) only records how the user entered it; a work day is 8 hours (480 minutes), defined in `apps/api/src/task/estimate.ts` and mirrored in `apps/web/src/lib/estimate.ts` (keep both equal). Both are accepted by the task create and full-update routes (omitted on update means untouched, `estimateMinutes: null` clears), reported in task responses and in the `task.updated` changes diff, and edited in the task details (`task-estimate-popover.tsx`). The Gantt uses the estimate for the display-only derived bars above and for the span of a task with one own date (next section). The MCP `create_task` and `update_task` tools accept both fields too (`apps/api/src/mcp/tools.ts`, vocabulary imported from `estimate.ts`): `update_task` forwards them only when provided, `estimateMinutes: null` clears the estimate, and the date-range rule above reaches the agent as the API's 400 message. `get_task` and `list_tasks` return them unchanged; `duplicate_task` and the other MCP task tools do not touch the estimate. A baseline is a user-triggered snapshot of current start/due dates, not a revision history; set and clear reuse `task.updated` (`apps/api/src/task/controllers/update-task-baseline.ts`). Constraints are `none`, `start_no_earlier_than`, `finish_no_later_than`, and `must_start_on` (`apps/api/src/task/schema.ts`). Calendar and constraint changes must preserve current task dates unless a specified operation explicitly moves them.

**Known proof gap:** the browser's drag/resize → cascade → persisted schedule → reload is not covered by the generic `scripts/ci/browser.mjs` flow. API persistence and pure cascade tests do not prove that full interaction. The dragged task is saved first and dependents are sent in a later bulk request, so the two writes are not one transaction. **Known boundary:** the API accepts validated bulk dates and does not independently enforce the Gantt dependency graph; other API clients can write dates inconsistent with `blocks`. Server authority and an atomic operation are accepted targets (DEC-SCHED-01 and DEC-SCHED-02), with implementation and contract design still pending.
