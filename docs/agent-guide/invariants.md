# Invariant index

Each ID has one home below. `enforced` means a named mechanism and relevant test support the stated scope; `partial` states a known proof or coverage gap. This is a small index of cross-surface behavior, not a claim that every possible invariant has been cataloged.

| ID | Behavior | Status | Mechanism / proof |
| --- | --- | --- | --- |
| KAN-AUTH-001 | Workspace-scoped relations cannot expose or link another workspace's tasks. | enforced | [API and boundaries](api-and-boundaries.md): endpoint membership checks and `tests/api-integration/task-relation-boundaries.test.ts`. |
| KAN-AUTH-002 | A non-owner cannot invite, re-send an invitation for, or assign a role whose permissions exceed their own, nor change their own role. | partial | [API and boundaries](api-and-boundaries.md): `assertCanAssignRole` runs in the `beforeCreateInvitation` and `beforeUpdateMemberRole` organization hooks (actor from the Better Auth endpoint context, so Bearer and API-key sessions are covered), and re-sends are checked in `hooks.before` via `auth.api.getSession` (a re-send authenticated with `x-api-key` counts twice against the key's rate limit and `remaining`); `apps/api/src/utils/role-delegation.ts` and `tests/api-integration/workspace-role-delegation.test.ts`; Kaneo API-key scopes are not intersected on Better Auth `/api/auth/*` routes, and composite roles are rejected rather than supported. |
| KAN-AUTH-003 | A user without full access sees and changes only projects they are a member of. | partial | [API and boundaries](api-and-boundaries.md): `resolveProjectAccess` in `apps/api/src/utils/project-access.ts`, applied by `workspaceAccess` (`apps/api/src/utils/workspace-access-middleware.ts`) and by the resolvers outside it (task relations, integrations `scopeToProjectFromBody`, WebSocket upgrade, asset download, bulk task update, task and project move); `tests/api-integration/project-membership-access.test.ts`, `project-member-api.test.ts`, `project-membership-lifecycle.test.ts`, `project-access.test.ts`. Workspace-level resources (`workspace`, `member`, `invitation`, `organization`, `ac`, `team`) are decided by the workspace role, with one explicit exception: the project member and project invitation routes check `member:*` and `invitation:*` against the caller's effective project statements themselves (and cap the workspace role they grant by the caller's workspace role). Stage 2b filters the list surfaces (project list, portfolio, search, workload, workspace activity and export, task and relation activity, workspace labels, relations and their targets, subtask counts, member list, notifications, assignee validation, duplicate and move) with `apps/api/src/utils/project-scope-filters.ts`, and revalidates WebSocket access, session and API key every 60 s on delivery: `tests/api-integration/project-scope-filters.test.ts`, `project-scope-websocket.test.ts`, `tests/api/ws/access-revocation.test.ts`. Known gaps: Better Auth `organization.listMembers` (web pickers) still lists the whole workspace, calendar feeds are not tied to their creator and account deletion does not close sockets at once, only within the 60 s revalidation (see the open list in [the plan](../plans/project-membership.md)). |
| KAN-AUTH-004 | A project invitation cannot grant a workspace or project role beyond the inviter's own permissions, and acceptance creates memberships only in projects of the invitation's workspace. | partial | [API and boundaries](api-and-boundaries.md): `apps/api/src/project-invitation/delegation.ts` (workspace role through `assertCanAssignRole`, project role through `assertAssignableProjectRole`, `owner` never; cancel and resend check the stored roles), `upsertInvitationProject` and the workspace filter in `apply-invitation-projects.ts`; `tests/api-integration/project-invitation.test.ts` and `project-invitation-accept.test.ts` (real Better Auth sessions for acceptance, mutation-checked for each rule). These routes are the explicit exception to "invitation is a workspace-level resource": `invitation:create` and `invitation:cancel` are evaluated on the caller's effective project statements, the workspace role granted stays capped by the inviter's workspace role. Acceptance refuses existing workspace members. Gaps: concurrent acceptance of two invitations to one workspace can still create duplicate member rows (Better Auth has no unique constraint on `workspace_member` and adding one to its table is out of scope for existing installations; duplicates that disagree on the role fail closed); a reverted acceptance clears the session's `activeOrganizationId` instead of restoring the previous one (the hook has no session); project invitations created before migration 0057 (unreleased) have no origin row and count as workspace invitations; the email is only proven to reach the mail helper, not an inbox; the race between acceptance and a project move (rows are read `FOR SHARE`) has no concurrent test; a failing revert after a failed membership insert is not tested; the rate limit counts per instance; API-key scope is tested for create only. |
| KAN-AUTH-005 | Inviting from a resource cannot grant more than the inviter holds, and linking moves only assignments in projects the account can access. | partial | [API and boundaries](api-and-boundaries.md): `POST /api/resource/{id}/invite` runs `createInvitationForProjects` (workspace role within the inviter's, each project role within the inviter's statements in THAT project, `invitation:create` in each project, all or nothing); `linkInvitedResources` and `linkResourceToMember` move only the assignments on tasks of the projects in the account's scope (`moveResourceAssignmentsToUser`), merging with the higher `units`; `tests/api-integration/resource-invitation.test.ts` (real Better Auth sessions, mutation-checked for the delegation checks, the merge rule, the project scope, the workload dedupe, the fold privacy and the upsert against a concurrent assignment). Gaps: the scope at acceptance is read from the memberships the same transaction wrote (no concurrent test of a project move meanwhile); events are published after the commit and a failing publish is only logged; two simultaneous invitations of one resource are serialized by the per-email lock but not tested concurrently; MCP has no tool for these routes; no browser pass of the dialogs. |
| KAN-AUTH-006 | Adding an existing account directly cannot grant a role above the caller's, and the user directory is reachable only with `member:create`, never by a guest account, and when enabled (direct add of a non-member needs the directory enabled too). | partial | [API and boundaries](api-and-boundaries.md): `assertAddableWorkspaceRole` and the `requireWorkspacePermission({ member: ["create"] })` gate of `POST /api/workspace/{id}/members` and `GET .../user-directory` in `apps/api/src/workspace/`, the workspace-role check of the project route in `apps/api/src/project-member/index.ts`, `isUserDirectoryEnabled` in `apps/api/src/utils/user-directory.ts`; `tests/api-integration/workspace-direct-add.test.ts`, `workspace-user-directory.test.ts`, `project-member-add-workspace.test.ts` (real API routes with Better Auth's `addMember`, mutation-checked for the delegation, the `member:create` and the guest gates; the limit of 30 adds per 10 minutes and the member limit are tested). Gaps: the directory reveals that an account exists, and a person can be added without consent, to ANY holder of `member:create` (a product decision: anybody who creates a workspace can see all names and emails; `DISABLE_USER_DIRECTORY` and `DISABLE_WORKSPACE_CREATION` are the controls); the add is not atomic with Better Auth's duplicate check (two simultaneous adds can create two member rows, the access rules fail closed); the workspace add of a project add is undone by compensation, not one transaction; the directory rate limit counts per instance; no browser pass of the dialog in CI. |
| KAN-SCHED-001 | Creating a `blocks` or `subtask` edge must not create a cycle in the workspace graph. | partial | [Scheduling](scheduling.md): `wouldCreateCycle` and cycle integration tests cover normal sequential creation; concurrent graph writes are not proven to serialize the read and insert. |
| KAN-SCHED-002 | A Gantt cascade moves only forward, retains task span and does not shift out-of-scope tasks. | partial | [Scheduling](scheduling.md): `computeDependencyCascade` pure tests; full drag-to-reload browser behavior remains unproven. |
| KAN-SCHED-003 | A batch schedule update writes validated dates together and publishes updates for affected tasks. | partial | [Scheduling](scheduling.md): transaction in `apps/api/src/task/controllers/bulk-update-tasks.ts` and `tests/api-integration/bulk-task-schedule.test.ts` cover success and invalid input; rollback after a mid-batch database failure and delivery after an event failure are not proven by that test. |
| KAN-SCHED-004 | A pushed dependent lands on a configured working day. | partial | [Scheduling](scheduling.md): `apps/web/src/components/gantt/gantt-working-calendar.ts` and cascade tests cover normal calendars; the API permits working-days mask `0`, for which the 366-day search cannot find a working day. |
| KAN-SCHED-005 | Schedule writes from every client respect the dependency graph. | unenforced | [Scheduling](scheduling.md): the API currently validates date ranges but does not independently enforce dependency consistency; DEC-SCHED-01 in [project decisions](project-decisions.md) is the accepted target. |
| KAN-SCHED-006 | A dragged task and its dependent cascade are persisted atomically. | unenforced | [Scheduling](scheduling.md): the UI currently sends two requests; the transaction for the later batch does not cover the initial drag. DEC-SCHED-02 in [project decisions](project-decisions.md) is the accepted target. |
| KAN-SCHED-007 | A cross-project `blocks` target within the same workspace joins the cascade. | unenforced | [Scheduling](scheduling.md): the current cascade sees only tasks from the active project. DEC-SCHED-03 in [project decisions](project-decisions.md) is the accepted target. |
| KAN-DATA-001 | A schema change works on existing data, not only a fresh installation. | partial | [Database](database.md): migration review and CI upgrade scenario; a particular change needs its own migration evidence. |
| KAN-DATA-002 | Every migration in the journal after the upstream baseline is applied on an existing database: its `when` is strictly greater than every earlier entry's. | partial | [Database](database.md): `scripts/ci/check-migration-order.mjs` and `scripts/ci/check-migration-order.test.mjs` (CI `unit` job, real journal) and the upstream-sync workflow. Gaps: the sync run reports and fails but cannot block a merge, whether the `unit` job is required is a repository setting, and the idempotency of re-issued SQL is not checked. |
| KAN-REALTIME-001 | Multi-project relations refresh clients subscribed to either project. | partial | [Web and realtime](web-and-realtime.md): second project event after relation creation; a complete two-browser interaction across projects is not in the generic browser CI flow. |
| KAN-RELEASE-001 | A development branch image is published only after CI passes for its source SHA. | unenforced | [Deployment and release](deployment.md): branch image publisher has no CI dependency. Preview tags are not release or test evidence. |

When changing a listed behavior, inspect the cited code and tests; update status only after adding the relevant proof. To add an ID, use `KAN-<AREA>-NNN`, include one unique index row, a concrete mechanism and a realistic test. Never change an ID just to rename its wording.
