# Web, realtime and translations

Use the typed client from `@kaneo/libs`, web requests in `apps/web/src/fetchers/`, and TanStack Query hooks for server state. For a mutation, check the response, query invalidation and optimistic state against a reload. Publish the appropriate event when a change drives activity, notification, integration or realtime updates; trace it from the API through WebSocket delivery to the affected project's/user's cache. The relevant patterns live under `apps/api/src/events/`, `apps/api/src/ws/` and `apps/web/src/hooks/`.

Redis is optional. A new realtime behavior must still work on one API instance without Redis, and must account for Redis fan-out if it spans API instances. For cross-project relations, both projects' subscribers may need refresh; see `apps/api/src/task-relation/controllers/create-task-relation.ts` and its second project notification.

A project socket is authorized once, at the upgrade; delivery in `apps/api/src/ws/index.ts` re-checks a connection's project access, session and API key when it was last confirmed more than `ACCESS_REVALIDATE_MS` ago (or its session expiry passed) and closes it (1008); a check that cannot be decided skips that message and is asked again, and three failures in a row close that connection (1011). Code that ends a user's access calls `closeUserProjectConnections` or `closeUserWorkspaceConnections` (project member removal and role change, workspace member removal, leave and role change already do) so sockets close at once on every instance; that instruction is a separate `control` envelope, never part of the client payload. A relation event is published through `publishRelationEvent`, which requires `projectTaskIds` (the relation's tasks in the event's project), and each project's subscribers receive only those ids.

**Gantt cache keys.** The Gantt reads `["tasks", projectId]`, the project-scoped relations `["task-relations", "project", projectId]` (its relation summaries carry each endpoint's dates, estimate, status and title, including endpoints in other projects of the workspace), `["calendar", workspaceId]` and the per-task `["task-relations", taskId]`. Build those keys only through `apps/web/src/lib/gantt-query-keys.ts`. A mutation that changes a task's dates, estimate, status, title, project or existence, or a relation, must call `invalidateGanttRelations`, because another project's Gantt may show that task only as a relation endpoint. The app default is `refetchOnMount: false`, so the Gantt queries opt in to `refetchOnMount: true`; without it a Gantt reopened after edits elsewhere showed the cached copy until a reload. `useProjectWebSocket` refreshes the project relations cache on `TASK_UPDATED`/`CREATED`/`DELETED`/`MOVED` and on relation events, and the API sends a project that holds only the other endpoint of a relation an id-free `TASK_RELATION_UPDATED` when a task's schedule, status or title changes (`getRelatedEndpointProjects`, `apps/api/src/ws/index.ts`; test `tests/api/ws/relation-endpoint-refresh.test.ts`). **Known gap:** no browser scenario covers the Gantt refreshing after an edit made on another page.

**Realtime refreshes and running fetches.** `useProjectWebSocket` sends every message- and reconnection-driven refresh through `createInvalidationBatcher` (`apps/web/src/lib/coalesced-invalidation.ts`): one refetch per key per 250 ms window, never an abort of a fetch that is running (TanStack's default `cancelRefetch: true` aborts and restarts a fetch of a query that holds data, so a burst of events could keep a 500-task page load from ever completing), and a query that is fetching is invalidated once more when its fetch settles so a change made mid-fetch is not lost. A reconnection catches up only after the socket stayed open `CATCH_UP_STABLE_MS`. `useGetTasks` does not forward the abort signal, because TanStack aborts a fetch that read it when the last observer unmounts, and a view that remounts during the first load would restart it forever. Views that read `useGetTasks` show `TasksLoading` while it has no data and `TasksLoadError` with a retry when it failed, never the empty state. Tests: `use-project-websocket-abort.test.tsx`, `coalesced-invalidation.test.tsx`, `use-get-tasks.test.tsx`, the Gantt route test.

**Gantt dependency neighborhood.** With a task open in the Gantt's details sheet, `GanttTaskNeighborhood` (`apps/web/src/components/gantt/gantt-task-neighborhood-card.tsx`, pure model in `gantt-task-neighborhood.ts`) draws a card over the blurred backdrop with the task's direct `blocks`/`related` predecessors and successors. It reads the schedules and relations the route already holds (no extra request, no new cache key) and routes edges through `buildDependencyEdges` and `GanttDependencyOverlay` (`showTypeLabels={false}`). `TaskDetailsSheet` takes it as the optional `backdropAside` and renders it inside the sheet popup, so it shares the focus trap and a press inside it is not an outside press (Base UI closes a modal only for a press on the backdrop or the viewport); other views pass nothing. The card positions itself against the popup (`end-full`, `100vw - 100%`) and is not drawn when that free area is under 480px. The card scrolls in one container (both axes, `overscroll-contain`, focusable and labelled): the date header and the task-name column are sticky, `buildNeighborhoodScale` never goes below `MIN_PIXELS_PER_DAY` so a long range overflows instead of shrinking, and the focus bar is scrolled into view when the card opens or the focus task changes. Base UI's scroll lock only sets `overflow: hidden` on `<html>`/`<body>`, so wheel input inside the popup is unaffected. Drag-to-pan starts on any mouse/pen press, including on a neighbor row: the rows are buttons that cover almost the whole chart, so excluding buttons left nothing to grab (jsdom could not show that); a 4px threshold keeps a click a click and a pan swallows its trailing click. A plain vertical wheel pans the time axis when only that axis overflows (a native non-passive listener; the browser would scroll nothing), and Ctrl/Cmd+wheel steps the scale. A Fit/Day/Week/Month/Quarter switch in the header picks the scale (`NeighborhoodZoom`, persisted per user as `ganttNeighborhoodZoom` in `useUserPreferencesStore` with a rehydrate guard); the unit scales (`UNIT_PIXELS_PER_DAY`) mirror the main Gantt's day-column widths and its header labels, and the focus bar is scrolled into view again after a scale change. A neighbor of the same project switches the sheet (`taskId` search param); a cross-project neighbor opens on its own project's task route. **Known gap:** covered by jsdom tests; the wheel, drag, scale switch and persistence were checked by hand in Chromium against a disposable local instance, but no browser scenario in CI checks the layout, scrolling or the backdrop click.

Web copy uses static i18n keys with `i18n/en-US.json` as the source of truth. When you add or change an English value, write the translation into every other locale file in the same change. `pnpm i18n:check:fix` only copies the English text as a placeholder; it does not translate. Run `pnpm i18n:check` and `pnpm i18n:untranslated:check` after changing catalogs. The second command fails on a value that is identical to en-US and is not in `scripts/i18n/untranslated-baseline.json` (the placeholders that existed when the check was introduced), and on a baseline entry that is no longer a placeholder. Run `pnpm i18n:untranslated:update` only to remove translated entries, or to accept a value that is correct in English in that locale (a brand name, for example); explain each accepted key in the PR. An upstream sync that brings untranslated keys fails the same check: translate them, or accept them with that explanation. Machine translations can be wrong; ask a speaker of the language to review them when possible. Retain keyboard access, accessible labels and empty/error/loading states. For a user-visible drag or resize, a focused pure-function test is useful but cannot alone prove the browser interaction and persistence; run a browser scenario when those are the behavior being changed.

Project views gate actions with `useProjectPermission(projectId)` (`GET /api/project/{projectId}/access`), not with the workspace role: a project member acts with the project role, and `useWorkspacePermission` stays for workspace-level actions (create project, resources, settings, members, roles). Pick people for a project (assignees, mentions) with `useProjectMembers(projectId)`, never with the whole workspace list. A project socket closed with 1008 invalidates `["project-access", projectId]` and the project list and leaves the project on 403 (`useProjectWebSocket`, `onAccessRevoked`); mutations that change who may do what in a project invalidate the same key (`projectAccessQueryKey`). See [project membership, stage 2d-1](../plans/project-membership.md).

The resources settings page (`apps/web/src/routes/_layout/_authenticated/dashboard/settings/workspace/resources.tsx`) shows a status badge per person resource and opens the invite and link dialogs (`apps/web/src/components/resource/`). The invite dialog offers the roles and projects the API lists for the caller (`assignable-roles` of the workspace and of each project, `invite-defaults`), and maps the API's error `code` to translated copy (`apps/web/src/lib/resource-error.ts`). Linking moves task assignments, so it refreshes the resource list, the task caches and the workload (`use-link-resource`); a resource linked to an account is left out of the assignee picker only in projects where the account is a project member (the person is picked there) and never while the task really has it (`getPickableResources`). The assignee picker (task popover and create-task modal) can also open the same invite dialog for a person resource with an email, right after creating it inline or from its row, with the task's project pre-selected (`defaultProjectIds`); it only opens the dialog for somebody who may create resources and invite to the project, never invites by itself, and the API still decides the roles and projects. See [stage 3](../plans/project-membership.md).

People management (stage 4): workspace and project members share `apps/web/src/components/people/`: `AddPeopleDialog` (one field; suggestions from the project member candidates and, when `userDirectoryEnabled` and the caller may add to the workspace, from the user directory; unknown emails are invited), `PeopleTable` with `WorkspacePeopleTable` and `ProjectPeopleTable`, and `PendingInvitations` with a workspace and a project adapter. The workspace page reads `GET /api/workspace/{id}/members?include=projects` (`useGetWorkspacePeople`, under the `["workspace-members", id]` prefix every people mutation already invalidates) and only the pending invitations still come from Better Auth. Gate the dialog with `canAddMembers` (workspace role) and the project abilities, never with hidden buttons alone. See [stage 4](../plans/project-membership.md).

Activity rows carry `actorVia` and `actorTokenHint` (see [API and boundaries](api-and-boundaries.md)); `ActorSource` (`apps/web/src/components/activity/actor-source.tsx`) renders the muted "(MCP · …a1b2)" or "(API · kaneo_ab…)" suffix after the actor in the task feed, comments and the workspace activity page, and nothing for the web UI.
