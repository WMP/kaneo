# Infrastructure capacity

Read this with [API and boundaries](api-and-boundaries.md) before changing `apps/api/src/infrastructure/`, the `infrastructure` or `datacenter` permission statements, or their tables. The target and the later stages are in [the infrastructure capacity plan](../plans/infrastructure-capacity.md).

A project owns its server model pool (`ganttpro_infra_model`), its hosts (`ganttpro_infra_host`, one unit of a model in one of the model's regions) and the VM items of its tasks (`ganttpro_infra_vm`). Project routes (`/api/infrastructure/project/{projectId}/...` through `workspaceAccess.fromProject`, `/api/infrastructure/task/{taskId}/vms` through `workspaceAccess.fromTaskId`) need `infrastructure:read`, `plan` or `manage`, a project-level resource judged by the caller's role IN the project, and every controller scopes ids by that project (another project's model or host answers 404). The datacenter routes (`/api/infrastructure/workspace/{workspaceId}/hosts...`) need `datacenter:read` or `manage`; `datacenter` is in `WORKSPACE_LEVEL_RESOURCES` (`apps/api/src/utils/require-workspace-permission.ts`), so only the workspace role decides it and a datacenter user sees hosts of every project of the workspace without project membership. These routes return project names, model data, host status and VM totals, never task titles. Only the built-in `owner` holds the new statements in code; stored `viewer`, `member` and `admin` rows are unchanged, so an administrator grants them in the role editor (Better Auth `update-role`).

Ceph storage clusters (`ganttpro_infra_storage_cluster`, `ganttpro_infra_storage_capacity`) belong to the workspace and are managed only through the datacenter routes (`/api/infrastructure/workspace/{workspaceId}/storage-clusters...`); a project sees only id, name, region and kind through `GET /api/infrastructure/project/{projectId}/storage-clusters`, never capacity or other projects' use. A VM's `cephStorageGb` counts against its cluster, `localStorageGb` (column `storage_gb`) against its host. The cluster must be in the task's workspace and in its host's region; the region of a cluster that VMs use cannot change.

Capacity (stage 2): the pure engine `apps/api/src/infrastructure/capacity.ts` (no database, no clock; `today` is a parameter) computes host and cluster use steps, warnings and the order plan; `controllers/capacity.ts` loads the data and builds the XLSX (`exceljs`). `GET /api/infrastructure/project/{projectId}/capacity` (`infrastructure:read`) returns only that project's hosts, VMs and task titles and names clusters by id and name only; `GET /api/infrastructure/workspace/{workspaceId}/capacity` and `.../order-plan.xlsx` (`datacenter:read`) return every project's hosts, the clusters and the order plan without task ids or titles. A VM's date is its task's start date, else its due date. `GET /api/project/{id}/access` reports `infrastructureRead`, `infrastructurePlan` and `infrastructureManage`.

Web: project settings › Infrastructure (`apps/web/src/components/infrastructure/project/`) and the task section (`components/infrastructure/task/`) use `useProjectPermission` (`canReadInfrastructure`, `canPlanInfrastructure`, `canManageInfrastructure`); the Datacenter page (`components/infrastructure/datacenter/`, route `workspace/$workspaceId/datacenter`) and its sidebar item use `useWorkspacePermission` (`datacenterRead`, `datacenterManage`) and send no request without read. Error codes map to translated text in `apps/web/src/lib/infrastructure-error.ts`, one map per surface. Every infrastructure query refetches on mount, every infrastructure mutation and the task mutations that delete, move, duplicate, archive or re-date a task invalidate the `["infrastructure"]` prefix (`invalidateInfrastructure`), and the project WebSocket does the same on task events, so a deleted host or task never lingers in a view. The infrastructure routes publish no events of their own yet. The create task modal lists VMs with the same editor (`components/infrastructure/task/vm-list-editor.tsx`) for `canPlanInfrastructure` in the chosen project and writes them with `PUT .../vms` only after the task is saved; a failure keeps the task and shows a toast, and switching the project clears the list.

The API, not the database, checks that a host's region is one of its model's regions and that a VM's host belongs to the project of the VM's task; `PUT .../vms` replaces the list in one transaction with the task row locked and persists nothing on a rejected item. Host status (`planned`, `ordered`, `installed`) changes only through the datacenter route; only a `planned` host can be deleted or change region. Errors carry a `code` (`apps/api/src/infrastructure/errors.ts`). The routes publish no events yet, and MCP has no tool for them until the order plan exists.

Region catalog: `ganttpro_infra_region` (migration `20261013130242_ganttpro_infrastructure_regions`, backfilled per workspace from the codes that models, hosts and clusters already use, name = code) holds the regions of a workspace. A code is 1 to 16 characters of `A-Z`, `0-9` and `-`, unique in the workspace and never changes. Model `regions` and cluster `region` must be in the catalog (400 `INFRA_REGION_UNKNOWN`, rows read `FOR SHARE`); deleting a region locks its row `FOR UPDATE` and answers 409 `INFRA_REGION_IN_USE` while a model lists it or a host or cluster uses it. `GET /api/infrastructure/workspace/{id}/regions` and its writes need `datacenter:read` and `datacenter:manage`; `GET /api/infrastructure/project/{id}/regions` (`infrastructure:read`) returns code and name only. `POST .../hosts` takes `quantity` (1 to 50) and returns `{ hosts }`; the labels continue the max+1 numbering, and a custom `label` needs quantity 1. Test: `infrastructure-regions.test.ts`.

Zones: migration `20261013140000_ganttpro_infrastructure_zones` adds `ganttpro_infra_region.zones` (jsonb, default `[]`) and the nullable `ganttpro_infra_host.zone`; it backfills nothing, so existing hosts keep a null zone. Zones are managed with the region (`datacenter:manage`; same code format, unique, at most 20); removing a zone that a host uses answers 409 `INFRA_ZONE_IN_USE` (region row locked `FOR UPDATE`). In a region with zones `POST .../hosts` needs `zones` (400 `INFRA_ZONE_REQUIRED`, `INFRA_ZONE_UNKNOWN`) and spreads the hosts round-robin; in a region without zones `zones` must be absent. `PUT .../hosts/{id}` changes region or zone only while `planned` (409 `INFRA_HOST_LOCKED`). Labels number per model, region and zone (`<model> <ram> GB <zone or region> #<n>`). VM and cluster checks compare regions only. Host responses, the order plan (grouped per zone) and the XLSX (column Zone after Region) carry the zone. Test: `infrastructure-zones.test.ts`.

Hypervisor reserve: migration `20261013170301_ganttpro_infrastructure_reserve_gb` adds `ganttpro_infra_model.hypervisor_reserve_gb` (default 8, check `>= 0 AND < ram_gb`). It backfills `LEAST(ram_gb - 1, CEIL(ram_gb * percent / 100.0))` before the check is added (usable RAM unchanged); the old `hypervisor_reserve_percent` column stays (deprecated, never read or written, dropped later) so an older binary can still insert. Usable RAM is `max(0, ramGb - hypervisorReserveGb)` (`capacity.ts`, mirrored in `apps/web/src/lib/infrastructure-host-usage.ts`); a reserve not below the RAM answers 400 `INFRA_RESERVE_TOO_LARGE`. Tests: `infrastructure-reserve.test.ts`, `infrastructure-reserve-migration.test.ts`.

Tests: `tests/api-integration/infrastructure-capacity.test.ts` (validation, scoping, cascades), `infrastructure-permissions.test.ts` (project role, workspace role, other workspace, datacenter without membership) `infrastructure-role-editor.test.ts` (the statements saved through the role editor are enforced) `infrastructure-storage.test.ts` (cluster visibility, erasure coding rules, capacity entries, VM cluster checks) and `infrastructure-capacity-plan.test.ts` (project and workspace separation, XLSX); unit tests of the engine in `tests/api/infrastructure/capacity.test.ts`. Known gaps: no events or realtime refresh yet; no browser test in CI; no concurrent test of two list replacements.
