# Jira integration

Read this with [API and boundaries](api-and-boundaries.md) before changing `apps/api/src/jira-integration/`, the Jira settings pages or the task Jira panel. The plan is in [the Jira plan](../plans/jira-integration.md).

Every user keeps a personal Jira token per workspace connection, encrypted with `NOTIFICATION_SECRET_ENCRYPTION_KEY` and never returned, logged, published in an event or sent to MCP; only `getJiraClientForUser` and `createJiraClientForToken` (`apps/api/src/jira-integration/tokens.ts`) decrypt it. Every request a user triggers (metadata, draft, send, refresh) uses THAT user's token; only the poll (`apps/api/src/scheduler/jira-status-poll.ts`) uses the token of the person who linked the issue (`createdByUserId`) and skips a link whose creator has none. Task routes need `task:read` (info, refresh) or `task:update` (draft, send, unlink) in the task's project through `workspaceAccess.fromTaskId`; proposal routes resolve the proposal's task first (`proposalAccess`, 404 when unknown) and need `task:update` there. Sending accepts typed values only and converts them on the server (`field-values.ts`). A Jira status change, from the public webhook (`/api/jira-integration/webhook/{connectionId}` with the secret in the query), the poll or a refresh, only reaches `processJiraStatusChange`: it records activity and a status proposal and never changes the task. Accepting the proposal does, through `updateTaskStatus`, claimed with a conditional UPDATE so a double accept answers 409. MCP has no Jira tool: a send needs a person's review and their own token.
