# Plan: project-level membership (model B)

Status: accepted by the product owner on 2026-09-29; stage 2a (single-project gate, member API, lifecycle) implemented on `claude/rbac-stage2a-core`, stage 2b (list and cross-project filters, WebSocket revalidation) on `claude/rbac-stage2b-lists`, stage 2c (project invitations) on `claude/rbac-stage2c-invites`, stage 2d pending, stage 3 (resources and invitations, "F4b") on `claude/rbac-stage3-resources`, stage 4 (unified people management) on `claude/rbac-stage4-people`. This plan describes the target. The [invariant index](../agent-guide/invariants.md) records what the code and tests enforce today.

## Goal

A workspace admin creates projects and invites people to a specific project with a chosen role, by link or email. An invited person signs in (for example through OIDC) and sees only the projects they belong to. A project member with the right permissions invites others to the same project, never above their own project role.

## Decisions

| Topic | Decision |
| --- | --- |
| Model | B: access to project data always comes from a project membership, except for full-access users (below). |
| Full access | Workspace owner, instance administrator, and any workspace role that grants `workspace:manage_settings` (the built-in `admin` has it). They see every project in the workspace and act with their workspace role. |
| Upgrade of existing installations | The migration creates the tables and **no rows**. Workspace owners, instance administrators and roles that grant `workspace:manage_settings` keep reaching every existing project through the full-access rule, so nothing is copied for them (a copied `admin` row would become a stale admin right after a demotion). **Every other existing member (built-in member and viewer, custom roles) loses access to all projects after the upgrade until an administrator adds them.** If a workspace edited its `admin` role and removed `workspace:manage_settings`, those admins are no longer full-access users, so after the upgrade they lose access to existing projects until they are added (a role row that cannot be parsed falls back to the built-in role and keeps the permission). Release notes and user documentation must say this. |
| Project creator | A creator without full access becomes a project member with the project role `admin`. A full-access creator gets no row: it already reaches every project, and a stored row would become a stale admin right after a demotion. |
| Project role | A name from the workspace role catalog (built-in `viewer`, `member`, `admin`, or a custom `workspace_role`). Its statements apply only inside that project. `owner` is never a project role. |
| Invitation to a project | The inviter chooses the workspace role and the project role. Both must be a subset of the inviter's own permissions: workspace role against the inviter's workspace role, project role against the inviter's effective role in that project. |
| Member list for restricted users | Only full-access members and members who share at least one project with the caller. |

## Access rule

`resolveProjectAccess(userId, projectId)` is the single source of truth:

1. No workspace membership and not an instance administrator: no access.
2. Instance administrator, owner, or workspace role with `workspace:manage_settings`: full access with the workspace role's statements.
3. A `ganttpro_project_member` row: access with the project role's statements.
4. Otherwise: no access.

Workspace membership is always checked first, so a stale project membership never grants access after a user leaves the workspace. Project-scoped permission checks (`requireWorkspacePermission` on a route that resolved a project) use the statements from this rule. Workspace-scoped actions (settings, roles, workspace invitations, creating projects) keep using the workspace role. API-key permission scopes are still intersected.

## Data model

New additive migration after `0055_ganttpro_resources`:

- `ganttpro_project_member(id, project_id → project cascade, user_id → user cascade, role, created_at)`, unique `(project_id, user_id)`, index on `user_id`.
- `ganttpro_invitation_project(id, invitation_id → invitation cascade, project_id → project cascade, role)`, unique `(invitation_id, project_id)`.
- Later stage, not in 0056: `ganttpro_calendar_feed.ganttpro_created_by` (nullable user id) so a feed stops serving when its creator loses project access. Legacy feeds without a creator keep working and are listed as a known gap.
- Both tables carry a `CHECK` that the role is not `owner`, also inside a composite name such as `admin,owner`. There is no backfill.

Removing a workspace member (remove, leave, account deletion) deletes that user's memberships in the workspace's projects. Moving a project to another workspace drops memberships of users who are not members of the target workspace.

## Stage 2a decisions and current state

- Project role that cannot be exercised (`owner`, or a name that no longer resolves in the workspace catalog) grants no access instead of read access without permissions. Moving a project to another workspace drops members who are not in the target workspace and members whose custom role does not exist there.
- Full-access users are listed by `GET /api/project/{id}/members` with `source: "full-access"` and their workspace role. They cannot be changed or removed at project level (400) and cannot be added as project members (409). A project row of such a user (for example from before a promotion) is inert.
- Workspace-level resources (`workspace`, `member`, `invitation`, `organization`, `ac`, `team`) are always evaluated against the workspace role, also inside a project request (a full-access caller's resolved access already holds that role's statements, so no extra lookup); a project role only carries `project`, `task`, `label` and similar. Managing integrations, reading their secrets and importing comments with external authors therefore stay with `workspace:manage_settings` in the workspace role. The project member API checks `member:*` against the project statements on its own.
- A workspace role that a project membership or a pending project invitation (by the workspace of the invited project) still names cannot be deleted; renaming it is refused as well (rename is blocked rather than synchronised). Both are enforced in `hooks.before` for `/organization/delete-role` and `/organization/update-role`, since Better Auth has no role hook. The guard answers only a caller Better Auth would allow (a member of that workspace holding `ac:delete` or `ac:update`, owners included; instance administrators get no special treatment because Better Auth gives them none) and skips only `owner`, since `viewer`, `member` and `admin` are dynamic catalog rows that can be deleted or renamed. It resolves the session with `auth.api.getSession`, which re-runs the API-key plugin's usage claim: a request authenticated with `x-api-key` counts twice against the key's rate limit and `remaining` (a known limitation shared with invitation re-sends); the error carries `code: "ROLE_IS_ASSIGNED_TO_PROJECT_MEMBERS"`.
- A project membership whose role grants nothing is listed with `active: false`; anybody with `member:delete` may remove it and anybody with `member:update` may re-assign it. Role changes and removals only touch the row that was checked and answer 409 if it changed meanwhile.
- Moving a project also drops its pending project invitations.
- Better Auth does not enforce one `workspace_member` row per user and workspace. Duplicates with the same role count once; duplicates that disagree on the role are ambiguous and count as no workspace membership (fail closed, instance administrators excepted) until an administrator fixes them. The member list shows each person once. "Role has an owner part" is one definition in SQL (`apps/api/src/utils/owner-role.ts`, also used by the CHECK constraints) and in `isOwnerRole`, compared in a test.
- Known window: `createProject` reads the creator's full-access status before its transaction; a role change in between yields either no admin row for a demoted creator or an inert row for a promoted one. Accepted.
- Removing a workspace member deletes their project memberships in that workspace in `beforeRemoveMember`; `/organization/leave` runs no organization hook and is handled in `hooks.after`. Account deletion cascades by foreign key.
- Also gated in 2a because they are single-project writes: creating a task label on a task (`POST /api/label` with `taskId`) and attaching a label to a task from the body (`label:update` in that task's project), creating a relation whose target lives in another project (`task:update` there), moving a task into another project (access plus `task:create` there), project move source and bulk task updates (every project).
- Events: no existing event type describes a membership change, so `POST/PATCH/DELETE /api/project/{id}/members` publish none. Realtime refresh and closing sockets of removed members belong to stage 2b.
- MCP and the typed client: no new MCP tools in 2a. MCP tools call the same HTTP routes and inherit the gate, but they cannot yet list or change project members; add tools together with the web UI in 2d if agents need them. The web client needs no change for the gate itself.
- Not yet covered in 2a, done in 2b (below): list, portfolio, search, workload and workspace activity filters, workspace member list for restricted users, relation targets and subtask counts, assignee validation, notifications, WebSocket delivery and close on removal, project reorder. Calendar feeds remain open.

## Stage 2b decisions and current state

Rule: a user without full access receives nothing from a project they are not a member of, not rows, counts, names, or the existence of a task on the far side of a relation. `accessibleProjectIds(userId, workspaceId)` is resolved once per request and turned into SQL by `projectScopeCondition` in `apps/api/src/utils/project-scope-filters.ts` (`null` adds no condition, an empty list matches nothing, one convention shared by `sqlIn`). A request that already resolved access to one project reuses it (`visibleProjectIdsFor`: full access is full access to the workspace, no second resolution). Predicates that span workspaces (search, notifications) use `resolveUserProjectScope` instead: the user's full-access workspaces plus the distinct (workspace, project role) pairs they hold, joined to `ganttpro_project_member` in SQL by `userProjectScopeSql`, so no project id list grows with the number of projects. Public routes (`isPublic`) are unchanged. MCP tools and API keys call the same HTTP routes and inherit every filter below (`tests/api-integration/project-scope-filters.test.ts`).

- Filtered: `GET /project` with its statistics, `GET /project/portfolio` (a dependency needs both projects), `GET /search` (`projectId` and `excludeProjectId` only narrow; with a workspace id the scope is resolved for that workspace only, and without one a user who belongs to no workspace resolves nothing; workspace results depend on membership only and are returned even without any project; an instance administrator who is not a member is full access), workload and its drill-through (`projectId` only narrows), workspace activity and its export, `GET /label/workspace/{workspaceId}`, `GET /task-relation/{taskId}`, `GET /task-relation/project/{projectId}`, the project task export, board subtask counters, notification list and mark-as-read.
- Workspace-level activity (no task, so tied to no project, for example calendar changes) stays visible to every caller who may read workspace activity. Workspace label definitions without a task stay too.
- `PUT /project/reorder` refuses an inaccessible id exactly like an unknown one (400, same message shape) and returns only the caller's projects. The ranks of projects the caller cannot see are kept.
- A relation to a task in an inaccessible project is dropped entirely, not redacted, from relation reads and the export. Relation activity (`relation_created|updated|deleted`, logged on the source task with the other task in its data) whose other task is in an inaccessible project is dropped from the task activity feed, workspace activity and its export, and search. Updating or deleting a relation loads both ends in one query and answers 404 when either end is inaccessible or the caller is outside the workspace, never 403.
- Notifications about a task need project access to be listed, created, mentioned or delivered on every channel: `notificationResourceAccess` takes the user's scope (`resolveUserProjectScope`), and `canReceiveResourceNotification` (used by `createNotification` and `deliverNotification`) calls `resolveProjectAccess`. Due-date reminders rely on that check and write the sent marker also for a user who cannot receive the reminder, as they do when reminders are switched off (windows are minutes wide, so skipping the marker would not have delivered it later either). Notification rules accept only accessible projects and no longer echo a stale stored selection; a rule that already selects projects can be saved with an empty selection (it then notifies about no project), a new rule or one switched to "selected" still needs one.
- Assignees: a new assignee must be able to open the task's project (`assertProjectAssignableUser`, `filterProjectAssignableUsers`) on create, update, assignee, assignees, bulk `updateAssignee` (per task's project, before anything is written) and import; instance administrators stay assignable. Only NEW assignees are checked. An assignee already on the task (update-task, the assignee list, and for a bulk assignment any task that already has them in its list, primary or not) is carried over with no check at all, neither project nor workspace membership: the web client sends the current assignees back with every edit, so checking them would make every edit of a task whose assignee left fail and stop others from being added; they can still be removed. Duplicating a task drops an assignee without access from the copy; moving a task removes assignees without access to the destination project (read and deleted inside the move's transaction, the primary mirror recomputed, the same `task.assignee_changed` or `task.unassigned` event a normal change publishes), like moving a project does. Every failure has the same message, whether the user does not exist, is in another workspace, or lacks the project. Mentions rely on the notification rule above.
- Workspace member list (`GET /workspace/{id}/members`, MCP `list_workspace_members`, workload rows): a restricted caller sees themselves, full-access members and members sharing at least one project with them; full-access callers and callers whose workspace role grants `member: create|update|delete` (they manage members) see everyone. Workload passes the scope it already resolved.
- Duplicate workspace membership rows follow the rule of `resolveProjectAccess` in every filter (`singleWorkspaceRole`, grouping through `groupRows`): equal rows are one membership, rows that disagree on the role count as no membership, so the workspace is left out of `resolveUserProjectScope` and the assignee check, and the workspace member list shows each user once and leaves ambiguous ones out.
- Board `getTasks` takes its project scope as a required argument (`"all"` explicitly for full access and the public board), so leaving it out is a type error.
- WebSocket: connections keep `validatedAt`, dated from the start of the last check, and the credential that opened them (API key id, or session id and expiry). Delivery re-runs `resolveProjectAccess` and re-reads the credential when the last check is older than `ACCESS_REVALIDATE_MS` (60 s) or the known session expiry passed (the session may have been extended, which the check reads back). A revoked or expired session, a disabled, deleted or expired API key, or lost project access closes the socket with 1008. One check per user and project and one per credential is shared by all sockets and concurrent deliveries. A check that fails for a transient reason skips that message for the connection and is asked again on the next delivery; a connection that fails three checks in a row is closed with 1011 (per connection, so an outage does not disconnect everyone at once) and its client reconnects and refetches. `closeUserProjectConnections` and `closeUserWorkspaceConnections` in `apps/api/src/ws/index.ts` close sockets at once on every instance, through a `control` envelope that is a different type from the client `message` (over the Redis channel with Redis, local otherwise); the issuing instance ignores its own echo. Relation events carry `projectTaskIds` (which of the relation's tasks live in the event's project, set by the create, update and delete controllers) the field is required by the typed `publishRelationEvent` (omitting it is a compile error), and the WebSocket layer sends only those ids without any lookup (an event without the list carries no relation id). The user socket carries no project data.

Open after 2b (each is an explicit gap, not a decision):

- Sockets close at once when project membership ends (project member removal, leaving a project, a project role that actually changed: `apps/api/src/project-member/controllers/`) and when workspace membership ends or changes (`afterRemoveMember`, `afterUpdateMemberRole` when the role changed, and the `/organization/leave` path in `apps/api/src/auth.ts`, so a demoted full-access user reconnects with fresh access). Not covered: account deletion; the open sockets close at the next delivery after the 60 s revalidation window (deleting the account also removes the session, which the credential check sees).
- The web assignee and mention pickers read Better Auth `organization.listMembers`, which returns the whole workspace; stage 2d switches them to a Kaneo route (or the filtered member list). Done in 2d-1 (below); the Better Auth list itself still answers a restricted caller with the whole workspace (a gap of the auth API, not of the pickers).
- Calendar feeds (`apps/api/src/calendar-feed/`) are public by token and are not tied to their creator, so a feed keeps serving a project's tasks after its creator lost access. Fixing it needs the `ganttpro_created_by` column planned above, so it belongs to a schema stage.
- Workspace resources (people, equipment, material) are workspace-level and are still listed to every workspace member, and workload lists person resources.

## Stage 2c decisions and current state

- Better Auth 1.6.25 hooks around acceptance (`routes/crud-invites.mjs`): after its own checks (pending, unexpired, session email equals the invitation email, membership limit) it calls `beforeAcceptInvitation({ invitation, user, organization })`, marks the invitation `accepted`, creates the member row in its own transaction (a failure there puts the status back to `pending`) and then calls `afterAcceptInvitation({ invitation, member, user, organization })`. Nothing rolls back after that hook, and accepting does not check whether the user already is a member (a duplicate member row would be created).
- `beforeAcceptInvitation` refuses somebody who already is a workspace member (409 `ALREADY_WORKSPACE_MEMBER`, plain workspace invitations too; the invitation stays pending), because Better Auth would add a duplicate member row and disagreeing duplicates count as no access. For everybody else it deletes their project memberships of the invitation's workspace: a fresh join must not revive rows an earlier membership left behind. `afterAcceptInvitation` runs one transaction: read the invitation's `ganttpro_invitation_project` rows `FOR SHARE` together with their projects, keep projects that still belong to the invitation's workspace and whose role still resolves, insert them (`ON CONFLICT (project_id, user_id) DO NOTHING`: an invitation never overwrites a row), delete every row of the invitation. Full-access people (owner, instance administrator, roles granting `workspace:manage_settings`) get no project row, like project creators and the member API's add: their workspace role already reaches every project, and a stored row would become a stale grant after a demotion.
- Failure behaviour: if the transaction fails, the acceptance is reverted (the member row Better Auth just created is deleted, the invitation is `pending` again, rows intact, and sessions Better Auth pointed at the workspace no longer name it as active) and the request fails with `PROJECT_INVITATION_NOT_APPLIED`, so the same link can be used again. If the revert fails too, the person stays a workspace member without projects (narrowing only), the invitation stays accepted with its rows, and an administrator adds them; both cases are logged. Only the first is tested.
- The invitation row is written by the project routes directly, not through Better Auth, so `apps/api/src/project-invitation/constants.ts` holds the 48 hour expiry and the 100 pending invitations that `auth.ts` also hands to Better Auth, and the cloud gates of `hooks.before` (guest accounts, disposable addresses) are applied in the controller. A live pending invitation for the same email and workspace role gets the project added (200, no second email); another workspace role answers 409 `INVITATION_ROLE_CONFLICT`; an expired one is ignored and a new invitation created, as Better Auth does. Creating, cancelling and resending for one email in one workspace take the same advisory lock.
- Sockets (stage 2b semantics): granting memberships on acceptance, the purge before a fresh join, cancelling and re-sending revoke nothing, so nothing closes. Only the revert of a failed acceptance takes a membership away and calls `closeUserWorkspaceConnections`, like a workspace member removal.
- Origin: `ganttpro_invitation_origin` (migration 0057, no backfill) has a row for every invitation created through the project routes. A trigger on `ganttpro_invitation_project` cancels a pending project-origin invitation when its last project row goes away (route, deleted project, moved project). A plain workspace invitation that had a project attached only loses that project, and a project may be attached to it only by somebody holding `invitation:create` in their workspace role (409 `WORKSPACE_INVITATION_EXISTS`). Accepted, canceled and other projects' invitations answer 404 on cancel and resend; cancel and resend judge the roles on the invitation row read under the per-email lock, cancel accepts roles that no longer resolve, and a re-send applies the cloud gates.
- Known limitations: concurrent acceptance of two invitations to one workspace can still create duplicate member rows (Better Auth has no unique constraint on `workspace_member`; adding one to its table is out of scope for existing installations, and disagreeing duplicates fail closed); a reverted acceptance clears the session's `activeOrganizationId` instead of restoring the previous value (the organization hook has no session); project invitations from before migration 0057 (unreleased, branch builds only) have no origin row and count as workspace invitations.
- Locking: create's attach path, cancel and resend take the per-email advisory lock and then lock the invitation row `FOR UPDATE` (the invitation-project row first, the order the origin trigger takes them in), re-checking that it is still pending, so the trigger's cancel from a project move or delete cannot interleave. An invitation canceled meanwhile makes cancel and resend answer 404 and create a new invitation. Role and standing lookups inside these transactions run on the transaction (`executor` parameter of the shared role helpers).
- Permission model: `invitation:create` and `invitation:cancel` (and `member:*`) are evaluated on the caller's effective PROJECT statements in these routes, an explicit exception to the workspace-level resource rule (a person invites within their own scope); the workspace role granted stays capped by the inviter's workspace role.
- Rate limit: creating and re-sending share 5 per minute per user, on cloud only like Better Auth's `rateLimit.customRules` for `invite-member`; the counters are in process memory (per instance, no Redis).
- Email: `apps/api/src/invitation/send-invitation-email.ts` is used by Better Auth's `sendInvitationEmail` and by the new routes. The email keeps the workspace copy: the templates and six locale catalogs have no project wording, and the accept page shows projects and roles (`projects` on `GET /api/invitation/{id}`, `/api/invitation/public/{id}` and `/api/invitation/pending`; the public route lists them only while the invitation can still be accepted). The response reports `emailAttempted` (false when SMTP is not configured, nothing was sent, or a project was added to an invitation that was already mailed) and `emailSent`. A failing relay is logged and does not fail the request; re-send retries.
- MCP and the typed client: no MCP tool in 2c. Inviting a person by email ends in a human accepting through the web, and Better Auth's own invitation routes have no MCP tool either; add tools together with the web UI in 2d if agents need them, as for project members. The typed client picks the routes up through `AppType`; the web UI belongs to 2d.

## Stage 2d-1 decisions and current state (project permissions and pickers in the web app)

- `GET /api/project/{projectId}/access` (`apps/api/src/project-member/controllers/get-project-access.ts`, gated by `workspaceAccess.fromProject`) returns `{ mode, role, capabilities }`. `ProjectAccess` carries the `role` behind the decision and the caller's `workspaceStatements`, both set in `decide()`; every capability is computed synchronously from it and the API key scope (no query). Task, label and project capabilities use the effective project statements; labels are split into `createLabels` (a label on a task), `attachLabels` (`label:update` in the project) and `manageWorkspaceLabels` (label definitions of the workspace, by the workspace role); `addMembers`, `manageMembers`, `inviteToProject` and `cancelProjectInvitations` use `projectStatementsDecision` (shared with the asserts of the member and invitation routes); `inviteToProject` is also false for a cloud guest (`isCloudGuest`; unknown for an API key request, which carries no session user, so the route still refuses); `manageIntegrations` is `workspace:manage_settings` in the workspace role, false for every project member without full access. Billing is not considered (an expired Kaneo Cloud plan still answers 402 on writes). `role` is the project role (member) or the workspace role (full). It is a hint for the UI: the API enforces every action again. No MCP tool: MCP tools call the routes themselves.
- Web: `useProjectPermission(projectId)` (`["project-access", projectId, userId]`, exported prefix `projectAccessQueryKey` for invalidation) replaces `useWorkspacePermission` in project views: task popovers, task details, subtasks, relations (also the Gantt and portfolio dependency popover, per source task), labels popover, context menu, column header and editor, bulk toolbars, create-task modal (the selected project), external links, GitLab import, calendar sharing, project general and visibility settings (moving a project needs `update` and `delete` in the project plus `project:create` in the target workspace by workspace role), the project row's delete item in the sidebar. `useWorkspacePermission` stays for workspace-level actions: create project, reorder, resources (`POST /resource` has no project), workspace settings, members, roles, invitations, labels settings.
- People pickers (assignee popovers, task cards and rows, bulk toolbars, create-task modal, comment mentions, properties sidebar, subtasks, relations) read `GET /api/project/{id}/members` through `useProjectMembers(projectId)` and drop `active: false` rows; workspace-level views (activity log and the names in activity feeds) read `GET /api/workspace/{id}/members` (filtered for restricted callers) through `useGetWorkspaceMembers`. Better Auth stays only where it manages people: the active member lookup (`listMembers`) and the members page (`getFullOrganization`). An assignee who is not a project member (left the project, or a related task of another project) is shown by the name and image the task carries (`findAssignee`), and the assignee popover keeps an already assigned person in the list with a hint so they can be unassigned. The create-task dialog stays open when the chosen project blocks creating (inline message, Create disabled); the picker does not mark such projects, which would need one access request per project.
- Realtime: a project socket closed with 1008 and the reason "Project access revoked" (other 1008 closes keep the ordinary reconnect) invalidates `["project-access", projectId]` and `["projects"]`, refetches the access, shows a translated toast (`common.projectAccess.*`), reconnects when the project is still reachable and navigates to the workspace dashboard on 403 (`useProjectWebSocket` option `onAccessRevoked`, `useProjectAccessRevoked`). A failed check that is not a refusal keeps the project open; a 401 is left to the auth flow, and while the check runs or after a refusal no focus, online or backoff signal opens another socket. Workspace role changes, role edits, member removal and ownership transfer invalidate `["project-access"]`, `["project-members"]` and `["workspace-members"]` (`invalidateAccessQueries`).
- Not covered: no browser pass (component and hook tests only); integrations pages of a project still render their forms for everybody (the API refuses), only the GitLab import button follows the project rights; the comment editor reads the project of a task from the task query cache when no `projectId` prop is given.

## Stage 3 decisions and current state (resources and invitations)

Product decisions (final): a person resource with an email can be invited from the resources settings; after acceptance `ganttpro_resource.ganttpro_user_id` is set to the new account; the resource's task assignments MOVE to the account (the resource stays linked); when the account already sits on the same task, one assignment is kept with the higher `units` and the `work` of whichever side has it (never the sum); the workload has ONE row for the account, and assignments still left on the linked resource count in it.

- Schema: migration `0058_ganttpro_resource_invitation` adds the nullable `ganttpro_resource.ganttpro_invitation_id` (FK to `invitation.id`, ON DELETE SET NULL, indexed). Nothing else changes; the resource email and the link column already existed. The email is now stored in lower case and only a person can have one (400 `RESOURCE_EMAIL_NOT_ALLOWED`; an address stored on another kind before this rule may stay or be cleared). Changing or clearing the email detaches the pending invitation from the resource (the invitation stays valid for its address).
- Invite: `POST /api/resource/{id}/invite { workspaceRole, projects: [{ projectId, role }] }` (1 to 100 projects, each once). The resource must be a person with an email and not linked (400 `RESOURCE_NOT_PERSON`, 400 `RESOURCE_HAS_NO_EMAIL`, 409 `RESOURCE_ALREADY_LINKED`). It is the project invitation core, refactored into `createInvitationForProjects` (the single-project route calls it with one grant, unchanged): one invitation with a `ganttpro_invitation_project` row per project and a `project` origin row, the cloud gates, the rate limit (shared with the project route), the pending limit, the per-email advisory lock, extending a live invitation of the same workspace role (200, no second email) and the email. Authorization: `project:update` in the workspace role (the resource management permission), then for EACH project the caller's own access, `invitation:create` in their effective statements of that project (API key scope included) and the project role within those statements, and the workspace role within the caller's own; one failing project rejects everything and nothing is written (tested). A project of another workspace answers like a project without access. An address that belongs to a workspace member is 409 `ALREADY_WORKSPACE_MEMBER` and the UI offers "Link to member". The resource row is locked in the invitation's transaction, re-checked (not linked, same address) and stores the invitation id.
- `GET /api/resource/{id}/invite-defaults` lists the projects the caller can invite to, each with `hasAssignments` (the resource has tasks there: the projects to pre-select), the resource's projects first. This extends the design's "projects with assignments" list to every invitable project, so the dialog has one source for its options; projects the caller cannot open or cannot invite to, and archived projects, are left out.
- Transfer (`resource/transfer-assignments.ts`): `moveResourceAssignmentsToUser` converts the resource's assignments on tasks of projects in the account's scope in place (an UPDATE of the same row inside a savepoint: id and creation time stay, so the creation order and with it the primary mirror stay stable), and only when the account already has a row on the task, or got one meanwhile (the UPDATE hits the unique key), merges into that row (an upsert on `(task_id, user_id)`, then the resource row is deleted), so an assignment added meanwhile cannot abort the acceptance. Locks: the task rows first (`FOR NO KEY UPDATE`, id order, as `update-task` does), then the assignment rows (`FOR UPDATE`, id order); `previousPrimaryId` is read after the task lock. The app's routes are not consistent with each other (the assignee routes touch assignment rows before `task.userId`), so no single order rules every deadlock out: the link transaction and the acceptance transaction run in `retryTransaction` (`utils/retry-transaction.ts`), at most 3 attempts, again on a deadlock (`40P01`) or a serialization failure (`40001`), and nothing outside the transaction happens before it commits; folds several resources linked to one account together, ignores tasks of another workspace, and recomputes `task.userId` with `recomputeTaskPrimaryAssignees`. Scope is the projects the account can open: for a full-access account every project, otherwise its project memberships. `mergeAssignmentAllocation`: the higher `units` wins (a tie keeps the account's row), `work` is the winner's, else the other side's.
- Acceptance: `afterAcceptProjectInvitation` now runs `applyInvitationProjects` and `linkInvitedResources` in ONE transaction (`applyInvitationProjects` takes an optional `executor` and returns `grantedProjectIds`; the new memberships are not visible outside that transaction, so the scope comes from what it just granted). A failing transfer rolls the memberships back too and takes the existing revert of the acceptance (`PROJECT_INVITATION_NOT_APPLIED`, invitation pending again, member row deleted): a resource problem can keep somebody from joining until it is fixed, which was preferred over joining with a half-moved set of assignments (tested with a failing transfer). Resources with this invitation id that are linked already only lose the invitation id.
- Events: after the commit, one `task.assignee_changed` per task whose assignee list or primary changed (`userAdded` or a different primary), with `addedAssigneeIds`, `removedAssigneeIds: []` and `source: "resource_link"`; a task where the account was assigned already and only the allocation merged publishes nothing (like a resource-only change in the assignee routes). The actor is the accepting account for an acceptance (its own tasks are re-attributed to it; an extended invitation can have been sent by somebody else) and the caller for a link; `source` is the literal type `AssigneeChangeSource`. The notification subscriber skips `source: "resource_link"`: the person's own tasks are re-attributed to them, not new work (activity, WebSocket clients and integrations still get the event). A failing publish is logged and never undoes the link.
- Link to member: `POST /api/resource/{id}/link { userId }` needs `project:update` and `member:update` in the workspace role (the web capability `linkResources` asks for exactly that) (decided: it decides which account holds the assignments; a caller who may manage members sees every member, so the picker needs nothing more), the user must be a workspace member (400 `NOT_A_WORKSPACE_MEMBER`, same reading as the access rule), the resource a person that is not linked (409 `RESOURCE_ALREADY_LINKED`). The same transfer with the account's project scope as it is now (`accessibleProjectIds`); the response has `movedTaskCount`. `POST /api/resource/{id}/unlink` (same permissions, 409 `RESOURCE_NOT_LINKED`) only clears the link: assignments that moved stay with the account, and the resource gets its own workload row again. A user can be linked to several resources; the transfer merges them per task.
- List: `GET /api/resource/workspace/{id}` (and create, update, delete) return `linked` (true for every caller), `userId` and `user` (id, name, email, image of the linked account, only when the caller may see that member by the members list rule; otherwise both are null and only `linked` tells) and `invitation` (`pending` or `expired` with `expiresAt`; null for none, canceled, rejected or accepted, and for a caller without `invitation:create` in the workspace role or in any project they can open, decided by `resourceViewer` only when a response has an invitation to show). The invitation id is never exposed (it is the accept link). The link response also lists `movedProjectIds`.
- Workload: `get-workspace-workload.ts` keys a person resource with a linked account by the account id, skips it from the extra rows and merges a task where the account and its resource both appear into one assignee (the higher `units`); the drill-through of an account also matches its linked resources' assignments. Resources not linked are unchanged. The stage-2b scope filters still apply to tasks. The fold happens only for a caller who may see the account under the members-list rule (`foldTargetId` and `loadVisibleAccountIds` in `resource/fold-linked-resources.ts`, shared by the aggregate and the drill-through): for anybody else the resource keeps a row of its own with its own name, and the drill-through of an account does not match its resources, so neither confirms who a resource is linked to.
- Web (resources settings): status badge (Not invited, Invited pending or expired, Linked to a member), Invite dialog (workspace role and, per project, a role from the respective assignable roles; the API error `code` mapped to translated copy; the accept link and the email delivery notice as in the workspace invite dialog), Link to member picker, Unlink confirmation; the email field only for a person; a linked resource is left out of the assignee picker only in projects where its account is a project member, and never while the task (as persisted, not as toggled in the open popover) still has it; the inline resource form asks for an email only for a person and maps the API's coded errors; Link to member is offered only with `project:update` and `member:update`; linking refreshes what an assignee change refreshes, scoped to the workspace and the projects whose tasks moved (`invalidateAssigneeCaches`: task lists, task details and activity feeds through the project of the cached task, every cached relation list, and the workspace's projects, calendar, portfolio, search and workload views; `notifications` is not touched, the person is not notified), and inviting also refreshes the workspace invitations. The invite dialog uses `useRoleChoice` (workspace role, and one per project row) and the project members UI's `useGetProjectAssignableRoles`; the resource routes answer coded JSON errors through `utils/coded-error.ts` (`codedError`, also for name required and not found: `RESOURCE_NAME_REQUIRED`, `RESOURCE_NOT_FOUND`, `WORKSPACE_NOT_FOUND`), the resource fetchers read them with `readProjectApiError`, and `lib/resource-error.ts` maps the codes to translated copy.
- Not supported / open: resend and cancel of the invitation from the resource (invite again after it expired, cancel from the project's invitations); unlinking does not move assignments back; removing a member, leaving and joining afresh clear the account's links on that workspace's resources (`unlinkUserResources`; nothing moves back, account deletion does it through ON DELETE SET NULL); no MCP tool (the routes are for a person in the web UI); no browser pass of the dialogs (component tests only); the concurrency of a project move during an acceptance is not tested.

## Stage 4 decisions and current state (unified people management)

Product decisions (final): (1) an existing Kaneo account can be added to a workspace WITHOUT an invitation; (2) it is found through a searchable directory of ALL accounts of the instance, with the mitigations below; (3) whoever holds `member:create` in their workspace role may add directly, with the usual delegation (the granted role within the caller's, `owner` never); (4) the added person gets an in-app notification and, when SMTP is configured, an email; (5) workspace and project use one pattern: one "Add people" dialog, one people table, one pending invitations section.

- **Product decision and its risk, stated plainly**: the directory lists ALL accounts of the instance to anybody who holds `member:create` in a workspace role, and direct add needs no consent of the added person. On an instance where anybody can register and create a workspace (the creator is its owner, so holds `member:create`), ANY user can therefore read the name and email of every account and add accounts to their own workspace, which notifies and emails them. The product owner accepted this for company instances with an informed choice. Controls: `DISABLE_USER_DIRECTORY=true` switches the search off (people are then only invited by email and workspace members added to projects), `DISABLE_WORKSPACE_CREATION=true` keeps strangers from owning a workspace; **an instance open to untrusted users should set `DISABLE_USER_DIRECTORY=true` and/or `DISABLE_WORKSPACE_CREATION=true`** (cloud has the directory off by default). Guest (anonymous) accounts are refused on the directory, the direct add and the project add to the workspace on every instance (403 `GUEST_NOT_ALLOWED`), whatever role they hold.
- **Limits on direct add**: 30 adds per 10 minutes per user on every instance, one budget for `POST /workspace/{id}/members` and the project route's add to the workspace (429 `RATE_LIMITED` with `Retry-After`; in-process counters, per instance); on cloud the invitation limit (5 per minute, shared with invitations) applies to both routes as well. All applicable limits are checked first and an attempt is counted only when every one allows it, so a request refused by one limit does not spend the other. The attempt is counted after every cheap refusal (guest, directory off, role, target validity, already a member, the cloud invitation gates), so refused requests never spend budget. Better Auth's `membershipLimit` (100 members by default, which accepting an invitation is subject to as well) answers 403 `WORKSPACE_MEMBER_LIMIT_REACHED` on both routes.
- **User directory** (`GET /api/workspace/{id}/user-directory?q=`, `workspace/controllers/search-user-directory.ts`): needs `member:create` in the WORKSPACE role (owner and instance administrator included, API key scope intersected), at least 2 characters after trimming, at most 20 results with only id, name, email and image, ordered by name; leaves out anonymous (guest) accounts, accounts banned right now (`banned` without an expired `banExpires`) and everybody who already is a member of the workspace (excluded rather than marked); `%`, `_` and `\` in the query are literal; rate limited to 120 searches per minute and user (in-process counters, every instance). **Privacy implication:** it reveals that an account exists, also one that shares no workspace with the searcher. Feature flag: `DISABLE_USER_DIRECTORY=true` turns it off (403 `USER_DIRECTORY_DISABLED`, wins over the other flag); on cloud (`KANEO_CLOUD=true`) it is off unless `ENABLE_USER_DIRECTORY=true`; `GET /api/config` exposes `userDirectoryEnabled` (`utils/user-directory.ts`). The Helm chart has `kaneo.env.disableUserDirectory`. The user documentation and `ENVIRONMENT_SETUP.md` state the privacy implication.
- **Direct add** (`POST /api/workspace/{id}/members { userId, role }`, `workspace/direct-add.ts`): `member:create` in the workspace role; role delegation through `assertWorkspaceRoleWithinCaller` (coded 403 `ROLE_EXCEEDS_YOUR_PERMISSIONS`, 400 `OWNER_ROLE_NOT_ALLOWED`, 400 `UNKNOWN_ROLE`, composite names are unknown); the user directory must be enabled (403 `USER_DIRECTORY_DISABLED` otherwise, on both routes, even for the owner: people are invited instead; adding existing workspace members to projects is unaffected); the target must be a real account that exists and is not banned, and one answer covers an unknown, a guest and a banned account (404 `USER_CANNOT_BE_ADDED`, same body for all three, so the response does not reveal which case applies), and not be a member (409 `ALREADY_WORKSPACE_MEMBER`); on cloud the invitation gates apply (guest callers, disposable addresses, 5 per minute per user, shared with invitations). The insert is Better Auth's server-side `auth.api.addMember` (1.6.25: server-only, checks the account exists, the membership by email and the limit, but nothing about the role, hence the checks above), so `afterAddMember` syncs the billed seats. Before it, `purgeLeftoversOfEarlierMembership` (the helper the accept hook uses for a fresh join) drops the person's stale project memberships and resource links in that workspace. After the add, `notifyMemberAdded` creates the notification `workspace_member_added` (resource: the workspace; `eventData` has workspace id and name, inviter name and role) and sends the email (`@kaneo/email` `sendMemberAddedEmail`, English and Polish copy under `invitations.memberAddedEmail`, other locales get English; link to `/dashboard/workspace/{id}`). Neither fails the add; the response reports `emailAttempted` and `emailSent`. Known limitation shared with invitation acceptance: Better Auth's duplicate check and insert are not atomic, so two simultaneous adds of one person can create two member rows (the access rules fail closed on duplicates that disagree on the role).
- **Project add of a non-member**: `POST /api/project/{id}/members` accepts `workspaceRole` for somebody who is not a workspace member. The caller needs `member:create` in the project role (as always) AND in the workspace role; the project role goes through `assertAssignableProjectRole`, the workspace role through the direct-add checks; both are validated before anything is written. The workspace add (above) comes first, then the project row; Better Auth owns the first write, so atomicity is compensation: a failing project step deletes the member row again, re-syncs the seats, closes the person's workspace sockets and notifies nobody (`undoAddUserToWorkspace`, tested). A workspace role that grants full access (`workspace:manage_settings`) adds the person to the workspace only (the row comes back with `source: "full-access"`), like every other path that never stores a project row for full-access people. `workspaceRole` for somebody who already is a workspace member answers 409 `ALREADY_WORKSPACE_MEMBER` instead of being ignored. The response carries `workspaceMemberAdded`, `emailAttempted`, `emailSent`.
- **Lists for the unified tables**: `GET /api/workspace/{id}/members` rows carry `memberId` (Better Auth member id, for role changes) and `joinedAt`; with `?include=projects` a caller who manages members (workspace role with `member: create|update|delete`) or has full access also gets per person `projects: { id, name, role }[]` (limited to projects the caller can open, memberships whose role grants nothing left out) and `fullAccess` (no list for full-access people); other callers get neither field, and the visibility rule of the list is unchanged. `GET /api/workspace/{id}/invitation-projects` (for the pending invitations list, which Better Auth's list cannot fill) returns per pending invitation the projects it grants with the project role, only for a caller holding `invitation:create` or `invitation:cancel` in the workspace role (empty otherwise) and only projects the caller can open; plain workspace invitations are left out. `GET /api/project/{id}/members` rows carry `workspaceRole` (full-access rows included, equal to `role`) and `joinedAt` (the membership's creation time, null for full-access rows); update and remove answer the same fields.
- **Web** (`apps/web/src/components/people/`): `AddPeopleDialog` (one field; suggestions from the project member candidates, and from the directory when it is enabled, the caller may add to the workspace and, in a project, add to the project; an address nobody matches can be invited; picking a person asks for the workspace role, the project role, or both; invitations keep the email delivery notice and the copyable link), `PeopleTable` with `WorkspacePeopleTable` (Projects column, project names with the project role or "Full access", shown when the API sent project data) and `ProjectPeopleTable` (Workspace role column for every row), `PendingInvitations` with a workspace and a project adapter (each keeps its own gating and resend/renew/invite again/cancel behaviour). Settings -> Workspace has a "Members" entry next to the sidebar one. No MCP tool: the routes are for a person in the web UI, like stage 2 and 3.
- **Not covered**: no browser pass of the new dialog unless stated in the PR, the capability "may add to the workspace" in the project view reads the ACTIVE workspace's role (`useWorkspacePermission`), the directory rate limit is per instance, and the other locale catalogs keep an older wording of `projectInvitations.errors.alreadyWorkspaceMember`.

## Enforcement surfaces

Gate (single project): every `workspaceAccess.from*` resolver in `apps/api/src/utils/workspace-access-middleware.ts` returns the project id together with the workspace id and applies the access rule. The resolvers outside that middleware are handled one by one: task relations, integrations `scopeToProjectFromBody`, WebSocket upgrade, asset access, project move target, bulk task updates.

Filter (many projects): project list, portfolio, search, workload, workspace activity and its export, workspace labels, relations and the existence of the task on the other side, subtask counts, notifications (`notificationResourceAccess`, `canReceiveResourceNotification`), due-date reminders, workspace member list, assignee validation (`assertAssignableUser` must require access to the task's project), task move target, WebSocket delivery, calendar feeds. MCP tools and API keys use the same HTTP routes and inherit the rules.

Public projects (`isPublic`) remain readable without an account.

## Risks

- Upgrade changes behavior for existing members (decision above). Test the migration against a populated database.
- A missed read path leaks data. The inventory in stage 2b is the checklist; each entry needs a test.
- Performance on large boards: access is resolved once per request; list filters use one `IN (subquery)` on indexed columns.
